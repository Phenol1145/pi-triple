# Pi-Triple 产品形态（v1.5 规划基线）

> 状态：2026-08-21 与用户对齐确认。本文件是产品决策基线，不是技术设计。

## 1. 一句话定位

基于**分化智力理论**的、多类型专业 Agent 自动化协作、自优化系统。

## 2. PTL 与 PTH

- **两个产品，保持分立。**
- **PTL = pi 环境管理工具**：
  - 环境、模板、session、扩展/skill 的创建与管理；
  - 通过 Skill 帮助用户智能化组织、调试和使用 PTH；
  - 保留调用 PTH 的便捷命令，但**不渲染 PTH 业务 UI**；
  - 目标用户：人类与 coding agent。
- **PTH = Agent 自动化协作 + 自优化系统**：
  - 任务/角色/记忆/工具/观测/知识摄入的完整系统；
  - 操作 PTH 的 CLI 与 Web 收敛到 **PTH 侧**。

## 3. 入口形态（站在 PTH 视角）

- **TUI：废弃。**
- **CLI：面向 PTL 和 coding agent**，用于调试与自动化。
- **Web：面向人类**，是 PTH 的人类操作入口，目标为 **PTH 完整操作台**：
  - 任务发布与协作
  - 知识摄入与自优化
  - Agent 协作与观测
  - 记忆/配置等系统面
  - 当前五页 Console 是起点，不是终态

## 4. 核心闭环

- **双引擎并重**：
  1. 任务自动化协作引擎（多角色 Agent 分工完成目标）
  2. 知识与自优化引擎（摄入→验证→晋升→复用）

## 5. 人类交互策略

- 不提供单一模式，而是**交互策略**：
  - **开发模式**：每个阶段人类都可介入、审批、回退；
  - **工作模式**：由用户自行决定审核策略；
  - 高风险动作必须有人类确认。

## 6. 部署形态

- 现在：**仅本机**（loopback-first 安全模型）。
- 未来：提供服务器部署版本。
- 服务端权限模型：**留白**，待本地版稳定后再定。

## 7. PTH Web 演进路径

- **先搬迁、再扩展**：
  1. 把现有 PTL Operator Console 代码迁移到 PTH 侧；
  2. 在不破坏现有五页能力的前提下逐步扩展为完整操作台；
  3. PTL 侧不再维护 PTH 业务 UI。

## 8. 下一迭代优先级

- **基础重构优先**：
  1. 协议/边界/文档（API v1、OpenAPI、契约测试继续固化）
  2. 产品边界（PTH 侧承载 Web/CLI，PTL 回归环境工具）
  3. 再动 UI 和功能

## 9. 开放问题（暂不决策）

- 服务器部署的权限模型：单管理员 / 多用户 / 多租户
- 观测历史保留策略：内存短窗口 / 24h 落盘 / 长期
- 多运行时支持范围：Docker/OrbStack/Podman/containerd 的优先级
- 版本命名与发布节奏
