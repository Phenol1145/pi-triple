评审人：qwen3.8-max

依据：context.md（上下文基线）+ alignment.md（三方异同对照）+ proposal-qwen3.8-max.md（本人方案，仅对照，不自评）
证据标注：（文件名:行号），行号取自本轮 panel 目录下的方案原文，已用 grep 逐条核实。

## 一、对 flash 方案

### 优点
1. **合规纪律三方最强**：§6 逐条自查既有裁决（主会话=组织者、机械/智能分工、记忆不变量、投递窗口），
   是唯一给出显式合规清单的方案；所有落点收敛到既有模块，无新存储层、无新执行环境、无新依赖。
2. **C 的批量操作表是成本最低的 PTC 近似物**：复用 sorter? 判别式返回先例（裁决 I5），
   op 白名单枚举、无解析器、无新表、防御性挂载（flash.md:60-63），与既有单操作语义兼容——增量不回归。
3. **D 的三道护栏是结构性裁决而非提示词**（flash.md:77-81）：harness 不可被模型 CRUD、
   奖惩只认验收者成果契约、策略与事实分离。第三条最锋利——直接点出 Factorio 作弊的固化路径
   是"动作序列变成 skill"，于是结构性禁止动作序列进 harness。
4. **诚实度高**：明说 C 是"最不自信的一条"并给两周无使用即拆除的回退条款（flash.md:87）；
   A 准备了"不做 v1 用 L1 凑合"的降级路径（flash.md:88）。
5. **实施顺序可验收**：C→A→B→D 每步有独立验收条款（flash.md:95-106）、可回退；
   D 放最后且"验收者就位前只观察不固化"，与冷启动不污染参照系的战略一致。

### 弱点
1. **C 自相矛盾（原子化 vs 失败不中断）**：§1 声称批量表把"认领→自检→拒绝/提交"固定序列"原子化"
   （flash.md:13），第 65 行再申"原子化收益"；但机制条款（flash.md:60）明确规定"任何一条失败不中断后续"。
   这是批量（batch），不是原子（atomic）——真正的原子序列在 flash 自己的机制里拿不到。
   采纳时必须纠正措辞，否则实现者会按"原子"去造事务。
2. **A 只答了半个问题**：flash 明文"否决任务执行中间态（变量/计数器）进记忆"，
   把它推给"L2 数据域或执行环境职责"（flash.md:34）——但通篇没有给 L2 任何机制。
   Prime 的 kernel state 主要承载的恰恰是变量态；flash 的 A 只覆盖"模型主动声明的事实片段"，
   变量态悬空，等于承认 RAM 需求的一半不做。
3. **A 的生命周期挂错载体**：`session:<sessionId>` 锚点是软约定、无外键，会话结束无人触发归档，
   只能等 TTL 兜底；TTL 挂"任务执行超时的 2 倍"（flash.md:28），长任务跨会话时工作记忆先于任务死亡。
   更根本的是：任务回流被另一 agent 重认领时，会话锚点直接失效——
   工作记忆挂会话与 B 的"可找回/可续派"目标互相拆台。
4. **B 档一价值虚**：flash 自认 session_ref 是 best-effort 展示字段、不参与状态机正确性（flash.md:90）；
   会话重启即失效，resumeTask 大概率返回 session-gone，任务回落到既有回流路径——
   即"找回"在最需要它的时刻（会话已死）必然失败。
   且"父会话向已认领 agent 的会话续派补充指示"（flash.md:43）机制未定义：跨会话注入走 comms 还是派发？
   档二（映射层）推迟到"随 PTH 运行时接线"（flash.md:44），无期。档一本质是展示列，不构成 B 的答案。
5. **E2 误判覆盖**：flash 声称"DSP 检索快照进 checkpoint 已覆盖 Prime 的程序化重访，零新工作"
   （flash.md:71）。这是误读：Prime 的可重访对象是完整逐字历史（append-only JSONL），
   检索快照只是检索结果的存档。联邦目前没有逐字转录存储——正是我 E1 指出的隐形前置依赖，
   flash 与 pro 双双漏掉。
6. **D 的输入端无噪声治理**：触发靠 agent 自报经验候选（flash.md:73-74），无信号阈值、无冷却，
   草稿区会被自利候选淹没；评价面只有 hitCount + template_id 通过率（flash.md:76），
   无下游指标挂钩、无追偿。flash 自己也承认"分级本身成为博弈面（agent 把策略伪装成记实）"
   （flash.md:91）而未解。

### 分歧裁决建议（flash）
- **吸收**：D 三护栏（尤其策略与事实分离，我的方案缺这条）；
  C 的"逐 op 判别式 + 失败不中断 + 两周拆除条款"（同时纠正"原子化"表述）；
  A 的零 schema 思路作为薄表方案被否时的降级路径。
- **拒绝**：工作记忆生命周期挂会话（必须挂任务）；B 档一作为 B 的答案（解决不了"找回与继续"）；
  "变量态归 L2"的口头分配（要么给机制，要么明说不做）；"检索快照=程序化重访"的覆盖判定。

## 二、对 pro 方案

### 优点
1. **D 的三方分离职责最清晰**（触发=记忆维护者 / 评价=分析者+审核矩阵 / 固化=分级，pro.md:88-107），
   且**回溯验证 + anti-pattern 条目**（pro.md:113）是三方案中唯一回答"固化错了怎么办"的机制。
2. **提案噪声治理务实**（pro.md:136）：≥3 次信号阈值、噪声标签、提案源冷却期，
   直接对准 LLM 模式识别的过拟合风险。
3. **E3 是三方最好的 E 项**（pro.md:153-155）：把"agent 可创建 skill"翻译成
   "开发者创建任务模板走公域审核链"——模板是可审计的声明式规范而非可执行代码，
   比 Prime 原教旨和完全禁止都好。
4. **自我批评诚实**：风险 4 的僵尸在途 + 孤儿回收扩展（pro.md:132）是真问题；
   风险 5 对六事项跨五模块的容量自评（pro.md:134）罕见地不膨胀。

### 弱点
1. **A 违反三方既有共识**：alignment.md 记录三方一致"拒绝独立 L4 工作记忆层"；
   pro 的 L2.5 独立表 + 独立 SDK 方法 wmSet/wmGet + 独立 DSP 注入声明 wmKeys（pro.md:22-31）
   就是一个新层，只是改了名字。
2. **A 与 B 自相矛盾（最狠一条）**：A 规定"会话结束 → WM 清空"（pro.md:33）；
   B 却要求恢复任务时"注入 WM 快照 + 已完成步骤摘要"（pro.md:58）。
   会话结束 WM 已清，快照从哪来？两项核心机制在同一份方案里互相取消，
   除非引入未声明的第三存储（那又回到新层问题）。
3. **B 的执行上下文没有写入者**：execution_context 声称"持续更新"（pro.md:62），但谁写？
   agent 无此纪律、系统层无转录存储——pro 全文没有意识到转录是前置依赖（同 flash 弱点 5 的盲区）。
   "WM 快照 + 已完成步骤摘要"（pro.md:58）由谁生成、何时生成、写在哪，全部悬空。
   B 建立在一个不存在的组件上。
4. **C 的 DSL 是三方成本最高的方案**：手写解析器（所引 expr.ts 先例我无法核实）、
   一门新语言的语法/错误语义/测试面；"全部成功或回滚"的原子语义与真实流程冲突
   （pro 风险 2 自己承认，pro.md:126），补救方案竟是给 DSL 加 WHEN/THEN/ELSE 分支——
   声明式语言长出控制流，复杂度向它声称要避免的图灵完备面单调收敛。
   而批量收益，flash 的 op 列表零解析器就能拿到。
5. **C 第二步保留 persistent Python 评估门**（pro.md:81、pro.md:163）：
   与三方共识"拒绝完整 IPython/PTC 代码执行面"相抵触——即使是远期评估，
   也把红线改成了虚线，给后续翻案留了口子。
6. **P0 排序证据不足**："WM 最急"的唯一论据是分析者工作模式需要它（pro.md:168）；
   但分析者角色尚未建造（context.md 自持态战略：先角色收敛）。
   为不存在的角色建 P0 基础设施，是需求倒挂。
7. **§5 对其他模型的预测全部反向**：pro 预测 flash 会"主张直接引入 persistent IPython kernel、
   跳过 DSL 阶段"（pro.md:247-248）——实际 flash 的否决线第一项就是"全面 IPython/PTC"
   （flash.md:148），且要求"若对方坚持模型写代码，请先给出沙箱方案"（flash.md:111）。
   pro 对设计空间的定位感失准，其分歧预告的可信度连带受损。
8. **E2 selfGoal 无成本闸门**（pro.md:143-145）：agent 可无限给自己注册周期性 scheduled_jobs，
   与"规则内获取最多货币"的经济纪律零挂钩，是资源滥用面；
   D 的"低影响改进分析者直接 approve"（pro.md:97）也没有给出高/低影响的分类规则，分级边界是空的。

### 分歧裁决建议（pro）
- **吸收**：D 的回溯验证/anti-pattern、提案噪声阈值与冷却、E3 模板创建走审核链、
  B 的僵尸/孤儿回收扩展。
- **拒绝**：L2.5 独立层（尤其会话生命周期）、DSL（以 flash 的 op 批量表替代）、
  execution_context 无写入者方案（以 context_ref + 转录替代）、
  persistent Python 评估门（红线钉死）、selfGoal 无闸门版。

## 三、综合

### 逐条裁决对照（速览）

| 问题 | flash | pro | 我的裁决 |
|---|---|---|---|
| A 工作记忆 | 会话作用域 L3 草稿（零 schema） | L2.5 独立表 + wmSet/wmGet | 骨架取我（任务生命周期薄表），flash 版可作降级试水，拒 pro |
| B 持久会话 | session_ref 展示列 + resumeTask | execution_context + tracked | 取我 B-lite（转录续跑），flash 列可并存，拒 pro |
| C 工具面 | op 白名单批量表 | SQL 风格 DSL + Python 评估门 | 机制取 flash，框架取我，拒 pro 两项 |
| D 自改进 | 观察/固化两层 + 三护栏 | 三方分离 + 噪声治理 | 骨架取我，护栏细节吸收两家 |
| 顺序 | C→A→B→D | P0=A+B | 取 flash 骨架 + 强制 E1 转录在 D 之前 |

### flash+pro 合起来比我的方案强在哪
1. **D 的细节护栏**：pro 的噪声治理 + 回溯验证、flash 的策略与事实分离，
   是我方案（refine 任务化 + 经济问责）没有的三条补丁。
   我的 D 骨架更强（复用六状态机、报酬挂钩下游指标、追偿），但细节密度不如两者之和。
2. **E 面更落地**：pro 的 E3（模板创建走审核链）比我的"公域 fork 试水"具体；
   flash 的 goal-progress 模板（flash.md:69）比我的 E 部分更可执行。
3. **C 的谦逊**：flash 的批量表 + 两周拆除条款，比我的"PTL 七动词 + 押金经济闸门"克制，
   且不发明新语言。

### 我的方案被它们挑战最狠的点
**C 的经济闸门**。flash 与 pro 的工具面方案都保持经济中性，只有我在工具面引入押金/计费。
这是新机制而非存量复用：context.md 的经济裁决（货币/奖惩/清零）并未授权认领面收押金——
我把"经济驱动"原则过度外推到了未裁决的表面；押金参数设错会直接抑制认领吞吐，
反而伤经济系统本身。**接受降级：第一版动词族不带计费，计费留作有观察数据后的二期裁决。**
次狠是 A：flash 的零 schema 比我的 L2 语义扩张便宜（我自己风险 2 也承认扩张可能牵动
store.ts 的水位线/审计假设）——但 flash 版覆盖不了变量态：若需求只是事实片段则 flash 赢，
若要覆盖中间态仍需我的薄表 working_state。

### 最终采纳建议（逐条）
- **A**：骨架取我（生命周期挂任务、submit 时 working_refs 晋升、薄表 working_state），
  吸收 flash"晋升只走既有沉淀管道"的纪律；拒绝 pro 的 L2.5 与会话生命周期（与其 B 矛盾）。
  若实测只需事实片段，可先用 flash 的零 schema 草稿参数化试水，不满足再上薄表。
- **B**：采纳我的 B-lite（context_ref + append-only 转录，E1 先行）；
  flash 的 session_ref 可作廉价展示性附加列并存；
  拒绝 pro 的 execution_context（无写入者）与 tracked 双模式（两套生命周期=双倍故障恢复）；
  吸收 pro 的孤儿回收扩展。
- **C**：机制取 flash（tasks? 端口 + op 白名单批量 + 逐 op 判别式 + 失败不中断 + 两周拆除条款），
  框架取我（单一入口收口、后续只加动词不加面）；
  拒绝 pro 的 DSL 与 Python 评估门；我的押金计费降级为二期观察项。
- **D**：骨架取我（refine 模板任务 + harness_changes 表 + 验收分离 + 报酬挂钩下游指标
  + 六状态机复用）；触发信号双源（flash 的 agent 草稿 + pro 的维护者扫描，均套 pro 的阈值/冷却）；
  固化分级取 flash（记实类/行为级）；加 pro 的 anti-pattern 回溯与 flash 的策略事实分离；
  人类闸门取我（经济宪法不可变）。
- **实施顺序**：C 收口（flash 机制）→ E1 转录（我）→ A → D 接线（角色就位后），B 常驻角色最后。
  与 flash 的 C→A→B→D 大体一致，但坚持**转录必须在 D 之前**——这是 flash 与 pro 双双漏掉的硬依赖。

## 四、诚实标注：我看不到的
1. 记忆 spec 全文：flash 引用的"草稿区 TTL/archived 语义/§8 映射层规划/DSP 检索快照裁决"
   （flash.md:28、44、71）均无法核实，只能假定属实。
2. pro 引用的 expr.ts 解析器先例是否存在、复杂度如何（pro.md:80）。
3. sorter? 端口与 contracts.ts 的实际形状（tasks? 扩展是否真如 flash 所说"防御性挂载即可"）。
4. scheduler/runner.ts 的 timed-trigger 骨架状态（这也是我自己方案的依赖，同样未核实）。
5. 模型对批量操作表的真实使用行为——flash 自己也不确定（flash.md:87），三方都在猜。
6. 当前工程容量与角色建造时间表——直接决定 D 与常驻角色的排期可行性，三方方案均基于各自假设。

## 一句话总结（最狠批评）
- **对 flash**：A 把变量态口头推给 L2 却半个机制不给、B 档一自认只是展示字段——
  最守纪律的方案恰好把 A、B 两个真问题都答成了"不做"。
- **对 pro**：A 规定会话结束清空 WM、B 又要求恢复时注入 WM 快照——
  两项核心机制在同一份方案里互相取消，而 B 的执行上下文连写入者都不存在。
