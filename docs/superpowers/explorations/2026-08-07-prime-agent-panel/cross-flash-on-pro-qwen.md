- 评审方法：逐项核对两方案与 context.md 已裁决原则、与任务池六状态机/记忆系统既有机制的一致性；对每处"声明"追查落点（表/端口/命令/角色）；对自相矛盾点标 Blocker/Important/Minor。

## 一、对 pro 方案（proposal-deepseek-v4-pro.md）

### 1.1 优点（真认同的点，含证据位置）

1. **"治理先于能力"的顺序论证**（pro §3 顺序逻辑第 2 条）："我们完全可以在自改进机制上线之前，先建好 proposal → 审核 → 固化的管道，但不接通'自动生成 proposal'的那一端"。这比我的"低风险机械增量优先"多一层治理视角，且与 Factorio 教训同构——先有闸门再开闸。吸收进 D 的落地前置，作为顺序纪律。
2. **WM 的 DSP 可选注入（SSP 声明 wmKeys）**（pro §A 第 4 条）：agent 显式声明哪些 key 进 DSP 投影区，其余留在私有 scratchpad。比我的"默认投影会话作用域条目"更省 token、更可控——投影是显式选择而非隐式全量，这是 pro 对 A 问题最实质的改进，采纳。
3. **"PTC 不是语法糖而是范式"的判断**（pro §1 第一判断）：指出"agent 每一次工具调用都是离散 function call，调用之间靠 LLM 上下文窗口串联，没有持久化中间状态"。判断本身正确，问题层次抬对了——虽然它给的载体（SQL 风格 DSL）我不认同（见弱点 1）。
4. **风险自评诚实且具体**：僵尸任务回收（§4 风险 4："stale 回收机制扩展——不仅回收超时的 claimed 任务，也回收 execution_context.sessionId 对应会话已不存在的孤儿在途任务"）是 B 类方案的真实坑，缓解方案成立；"DSL 受控性可能是幻觉"（§4 风险 2）是自揭伤疤；proposal 噪声冷却期（§4 风险 3："连续被打标签的 proposal 源进入冷却期"）可移植。
5. **D 的三方分离**（§D：触发=记忆维护者/评价=分析者+公域审核矩阵/执行=op 手动）与我的"观察在智能层、固化在治理层"一致；且"固化输出永远不进正式态自动生效"是三方最严的治理条款，我倾向它的保守而非 qwen 的"低风险自动验收"。
6. **附录裁决记录表**（§附录）：把所有关键裁决浓缩成一张备查表，可操作性强——这本身是可移植的好实践。

### 1.2 弱点（自相矛盾 / 落不了地 / 违反既有裁决）

1. **[Blocker] 自相矛盾 A：DSL 原子性 vs 六状态机**。pro §C 说"声明式操作序列原子执行（全部成功或全部回滚）"，但 §4 风险 2 自己承认"认领 3 个任务但只能完成 2 个，第三个需要 reject"时原子性冲突；缓解给 WHEN...THEN...ELSE 或 PER_TASK vs ALL_OR_NOTHING——后者已把 DSL 推向图灵完备方向，等于自己拆了自己"DSL 是受控中间态"的论点。更致命的是：ALL_OR_NOTHING 的回滚需要"撤销 submit"这类转移，而 tasks 六状态机（pending→claimed→submitted→completed/rejected）没有 submitted→claimed 转移——DSL 要么违反既有状态机裁决（context：六状态机是已落地机制），要么需要新增转移。我的"逐条失败不中断后续、模型自行决定下一步"方案绕开了这个坑，pro 没有绕开。
2. **[Blocker] 自相矛盾 B：execution_context 跨 agent 注入 vs WM 会话生命周期**。pro §A 明确"WM 默认跟随 agent 会话生命周期（会话结束 → WM 清空）"，§B 又说"恢复时将 execution_context 中的关键状态（WM 快照 + 已完成步骤摘要）注入 agent 会话的起始上下文"且可"重新派发给原角色类型的另一个 agent"——会话结束 WM 已清空，注入什么？若 WM 在会话结束前被外部快照，那"会话结束即清空"就不成立，两个机制直接冲突。qwen 用"转录档案（持久的是档案不是进程）"绕开此矛盾，pro 没有。
3. **[Important] 违反治理直觉：分析者当 D 的评价器（激励盲区）**。pro §D 第 2 条让"分析者角色消费 proposal 条目 → 评估 → 产出评审意见"。但分析者的既有职责是拆分/合并任务且"受奖惩"（context 裁决 3：分析者拆分/合并权限受奖惩）；让它评估改进提案 = 赋予它影响其他 agent 行为与收益分配的权力，reward hacking 面从 agent 转移到评价者。pro 的防 hack 设计（固化不自动生效、经济目标约束）只覆盖"固化端"，没覆盖"评价者本身的激励"——qwen 用验收者分离 + 报酬挂钩下游指标补上了这一层，pro 没有。
4. **[Important] 落不了地：B 的"长期存在"存在循环依赖**。pro §B 第 5 条："持久 agent 会话内部可注册周期性自检任务（如每 5 分钟检查子任务完成情况）"——会话若已结束，谁注册？若注册发生在会话存活期，那与 fire-and-forget + 既有定时投递（scheduled_jobs）有何区别？pro 没有定义"会话内部注册"的机械执行者，这条落不了地。
5. **[Minor] 自我矛盾：工作量评估 vs 实施顺序**。pro §4 风险 5 说"改动跨 5 大模块、schema ≥2 列 2 表、SDK ≥5 方法、工程容量可能是瓶颈"，但 §3 第一阶段 P0 就并行 A+B 两个大项，与它自己"严格分批、单阶段完成+绿+commit 后再进下一阶段"矛盾。qwen"每步 ≤20 分钟实现量"的粒度纪律更可执行。
6. **[Minor] E2 selfGoal 与既有机制边界未划清**：pro §E2 说 agent 通过 `/lab goal set` 给自己注册周期性目标——这与"主会话=组织者"裁决中"派发=工具调用语义"的关系未说明：goal set 是 agent 主动行为还是组织者行为？若 agent 可自由注册目标，可能绕过任务池的认领/验收闭环产生无主任务。

### 1.3 与 pro 的分歧裁决建议

- **吸收**：治理先于能力的顺序；wmKeys 可选 DSP 注入；"固化不自动生效"+"anti-pattern 回溯验证"（§D 防 hack 第 4 条）；僵尸任务回收并入 stale 回收（§4 风险 4 缓解方案成立）；附录裁决记录表实践。
- **拒绝**：SQL 风格 DSL + 原子事务（与六状态机冲突，用批量操作表/动词族替代）；execution_context 跨 agent 注入（用 qwen 的 context_ref 转录替代）；分析者当 D 评价器（用 qwen 的验收者 + 激励挂钩替代）。

## 二、对 qwen 方案（proposal-qwen3.8-max.md）

### 2.1 优点（真认同的点，含证据位置）

1. **"持久性的单位是任务，不是会话"**（qwen §1 启发一）："任务池的六状态机本身就是持久身份……sqlite 落盘 vs 内存进程"。这是三方里最锋利的一个洞察——把问题从"要不要持久会话"重定义为"持久什么"，直接否决 rlm() 普适移植，与我的"持久身份落在账本不落在进程"同构但表述更根本。
2. **C 的动词族收口 + 经济闸门**（qwen §C）："认领要押金、查询免费、提交返还，把经济驱动前置到工具面本身——这是 Prime 完全没有的维度"。动词表（claim/submit/reject/query/recall/remember/sediment）与我的 op 白名单批量表是同一件事的两种表述，但它的"收口"意识（四个风格各异的工具面→一个入口 + 动词表）比我系统，且"只收口表面、不重写引擎"的克制正确。
3. **D 的激励设计最锋利**（qwen §D）："报酬与提案被采纳后的下游指标挂钩（同类任务完成率提升、拒绝率下降），而不是与'提出提案'这个动作挂钩"+"禁止 refine 提案修改自己的评价指标——硬编码进 ruleRef 校验"。直接补上 pro 的激励盲区，也比我"奖惩只认验收"多一层防博弈条款。这是全 panel 对 reward hacking 最具体的回答。
4. **E1 转录是隐形前置依赖**（qwen §E1 + §3 关键纪律）："B-lite 和 D 都依赖 append-only 转录，但仓库目前没有一个统一的 session transcript store……这一步应在 B/D 任何功能之前做"。三方唯一指出这个前置依赖的点。我的 D 只说"接线既有机制"，没给轨迹分析的数据载体；qwen 补上了这个洞。我承认这是我最实质的盲区之一。
5. **六状态机原样复用为提案状态机**（qwen §D 第 3 条）："这是把现有任务六状态机原样复用为提案状态机，不是新发明的流程"——设计美学正确，与"任务池与任务模板 id 同域"裁决一致，且 pending→claimed→submitted→completed/rejected 的六态正好覆盖提案生命周期。
6. **转录格式规格 E3**（{ts, claim_id, role, kind, payload}，kind ∈ {msg, tool, ptl, decision}，decision 事件为轨迹分析提供锚点）——比 pro 的"execution_context JSON"更具体，且"ingest 侧不需要任何改动"的边界声明清晰。

### 2.2 弱点（自相矛盾 / 落不了地 / 违反既有裁决）

1. **[Important] 自相矛盾 A：A 的"改造式支持"内部摇摆**。qwen §A 先反对"新建一个与 L1/L2/L3 并列的工作记忆子系统——那是架构税"，随即给出 `working_state` 表 SQL 作"退路"——这就是它自己反对的新表。摇摆本身不是错（它明说保留弹性），但没给出"何时扩 store.ts、何时建薄表"的判定条件，落地方案悬空。对照 pro：pro 明确选独立表，qwen 在两条路之间没有决策点。
2. **[Blocker] 落不了地 B：WM 绑任务生命周期牺牲分析者综合阶段**。qwen §A："TTL 绑定任务生命周期（任务 completed/rejected 时由沉淀管道决定升级或丢弃）"+"工作记忆的生命周期永远挂在任务上，不挂在会话上"。在"分析者拆分→收集各子任务结果→综合判断"这一核心工作模式（context 明示分析者职责）里这是反的：子任务 completed 时其中间结果即被升级/丢弃，综合阶段反而没有 RAM 可用。qwen 为 B 的自洽牺牲了 A 的实际用途——pro 的"绑会话"在这一场景更贴分析者工作模式。
3. **[Important] 落不了地 C：常驻角色判据不可操作 + daemon 后门论证不足**。qwen §B："判据：一个角色是否值得常驻，看它'跨任务状态量 / 任务频率'的比值，写进任务模板的执行协议字段"——谁计算？阈值多少？没有定义计算器或阈值来源，把决策责任推给一个不存在的计算器。且给分析者/记忆维护者开常驻会话 + heartbeat 与它自己"反对 rlm() 式普适持久子会话"的立场需要更多论证：分析者的工作模式恰是分散多任务（拆分→派发→等待），不是连续流，凭什么值得进程常驻？我维持反对，除非冷启动后有数据。
4. **[Important] 隐性依赖：押金闸门依赖未落地的货币系统**。context 裁决："任务池与任务模板 id 同域（未来与经济 elo 赛道联动）"——经济是"未来联动"状态。qwen 把"认领要押金"排进 C 第一优先级，但押金需要货币冻结/结算机制（新 schema/新表）；qwen 说"零新依赖"但没说零新 schema——C 的"无依赖"声明不成立。落地应缓到货币系统就位。
5. **[Minor] 语义洞：recall 与回流轮的关系未定义**。分选器已有回流轮（rejected 自动回流，context 裁决：回流轮 + stale 回收）；recall（主动退回、扣押金）的任务是直接回 pool 还是进回流轮？状态转移路径缺失；reject（附理由）与 recall（扣押金）的边界（同一任务先 recall 后 reject？）也没定义。
6. **[Minor] D 的"低风险自动验收"边界模糊**。qwen §4 风险 3 缓解："低风险（记忆条目）走自动验收，高风险（模板协议/经济参数）走人类闸门"——但"低/高风险"的划分标准没写死，与它自己"评价指标由任务模板预先声明、硬编码进 ruleRef"的严谨形成落差；边界若由 ruleRef 判定，谁来维护 ruleRef 的边界条目本身？应有 operator 在模板注册时定死（吸收 pro 的 meta 审核循环思路）。

### 2.3 与 qwen 的分歧裁决建议

- **吸收**："持久的是档案不是进程"（context_ref 转录）；经济闸门前置到工具面的方向（落地缓到货币系统就位，先把动词族/收口做了）；"评价指标不可自改"硬编码；E1 转录前置排序；六状态机复用为提案状态机；E3 转录格式规格。
- **拒绝**：WM 绑任务生命周期（改为 pro 的绑会话 + qwen 的"submit 时按 working_refs 决定升级或丢弃"钩子，各取一半）；常驻角色 daemon 后门（无数据不常驻，冷启动后用数据检验）；押金机制前置（货币系统未落地前只做动词族不做计费）。

## 三、综合

### 3.1 pro+qwen 合起来比我的方案强在哪里

1. **实施依赖分析比我细**：我的 C→A→B→D 是"低风险优先"排序；qwen 指出 D 的真实前置是转录（我没有），pro 指出治理先于能力（我有类似立场但没排进顺序）。两者合起来给出完整依赖链：C（收口）→ E1（转录）→ A（WM）→ B（档一）→ D（接线，治理先于自动化）。
2. **激励与反 hack 比我更可落地**：我的三道护栏偏原则（"harness 不可被模型 CRUD""奖惩只认验收""策略与事实分离"）；qwen 的"评价指标不可自改硬编码"与 pro 的"anti-pattern 回溯 + 噪声冷却期"是机制级的。原则需要机制落地，这两份补上了。
3. **经济维度**：qwen 的工具面计费是三方唯一的经济设计；pro 的"固化不自动生效"是三方最严治理条款。我的经济面只有"token=货币"监控，最薄。
4. **A 的可选注入**：pro 的 wmKeys 比我的"默认投影会话作用域"省 token、可审计。
5. **转录作为 B/D 公共前置**：qwen 的 E1 让 B 的"续跑"与 D 的"轨迹分析"共用一份数据载体，我的 session_ref 只有句柄没有数据，续跑语义比 qwen 薄。

### 3.2 我的方案被它们挑战最狠的点

1. **A 复用 L3 草稿（session 作用域）语义混槽**：pro 打"WM 不参与版本化/CAS，本就不是记忆语义，塞草稿区污染检索"；qwen 打"草稿区是待提升的语义条目，工作记忆是会话中间态，强行共槽"——两条路径打到同一个点，我的风险自评 2 自己也承认了。结论：**A 应让渡**——独立薄表（pro/qwen 形态）+ 我的"模型主动声明"语义 + pro 的 wmKeys 注入 + qwen 的 submit 晋升钩子，比我的零 schema 方案干净。这是我的方案最脆的一条，被双方以不同理由击中。
2. **C 的批量操作表被质疑"够不够"**：pro 认为 DSL 才给 agent 复杂编排能力（我不认同——批量表就是受控组合，组合权在模型侧、执行权在机械侧）；qwen 认为要"收口"（我认同，批量表就是收口的一种形态）。这条三方其实同构，反而是 pro 的原子事务设计最危险（违反状态机），我的"逐条失败不中断"最稳。被挑战的力度其实弱于 A。
3. **B 的"反对常驻 daemon"被 qwen 部分挑战**：qwen 第一个指出"跨任务连续状态"这个真实需求并给两个角色开常驻后门。虽然我不同意无数据常驻，但"高频角色需要跨任务状态"这个需求我低估了——应作为冷启动阶段的测量项，而非直接否决。这是三方里对我"账本承载一切"假设最实质的修正。

### 3.3 最终采纳建议（逐条 A/B/C/D）

- **A 工作记忆**：取 **pro**（独立 WM 表 + TTL + 会话生命周期 + wmKeys 可选 DSP 注入），吸收 **qwen** 的"submit 时按 working_refs 由沉淀管道决定升级或丢弃"钩子；拒绝我的"复用 L3 草稿"（语义混槽，被双方挑战成功）与 qwen 的"TTL 绑任务"（牺牲综合阶段）。理由：分析者工作模式需要跨子任务的会话级 RAM；pro 表 + qwen 钩子语义最干净，成本 1 表 + 2 SDK 方法，可接受。代价：承认零 schema 红线在 A 上让位——这是本评审对我自己方案的最大让步。
- **B 持久会话**：取 **qwen** 的 context_ref（转录档案，冷读续跑）+ 我的 session_ref 档一（句柄 + resumeTask）混合；拒绝 pro 的 execution_context 注入（与 WM 会话生命周期自相矛盾）与 qwen 的常驻 daemon 后门（无数据不常驻）。理由：档案承载"找回/继续"、句柄承载"续派指示"，两层都薄且互不纠缠；转录同时服务 D。
- **C 工具面**：取 **我的批量操作表 + qwen 的动词族收口**（同一件事：op 白名单 + 判别式返回 + 单入口），经济闸门缓到货币系统就位；拒绝 pro 的 SQL DSL 原子事务（违反六状态机）。理由：pro 的 DSL 要么违反状态机要么滑向图灵完备；批量表/动词族是同一受控组合语义，零新依赖零新表。
- **D 自改进**：取 **qwen** 的"refine 即任务 + 报酬挂钩下游指标 + 评价指标不可自改硬编码"、**我的**"harness 不可被模型 CRUD + 奖惩只认验收者成果契约"、**pro** 的"固化不自动生效 + anti-pattern 回溯 + 噪声冷却期"；拒绝 pro 的"分析者当评价器"（激励冲突）与 qwen 的"低风险自动验收"边界模糊（分级保留，但高低风险边界由 operator 在模板注册时定死）。理由：三方共识是治理闸门；qwen 的激励设计最锋利、我的护栏最结构性、pro 的回溯最完整，合并后 reward hacking 面覆盖到 agent 与评价者两层。
- **实施顺序（综合三方）**：C 收口（无依赖，收益最早）→ E1 转录（B/D 共同前置，qwen 洞察）→ A WM（pro 表）→ B 档一（session_ref + context_ref）→ D 接线（验收者角色就位后，治理先于自动化）。这条顺序吸收了 qwen 的前置分析、pro 的治理纪律、我的低风险优先，是三方顺序的交集。

### 3.4 对 alignment.md 协调者汇总的核对

1. **汇总基本准确**：三方共同点（拒绝自主 /refine、拒绝 IPython、拒绝普适 rlm、拒绝独立 L4、refine 治理化）与两方案原文一致，无夸大。

## 五、给协调者的裁决锚点（一句话总结）

**采纳线**：A 取 pro 表 + qwen 晋升钩子；B 取 qwen 转录档案 + flash session_ref 句柄；C 取 flash 批量表 + qwen 动词族收口（经济闸门缓行）；D 取三方精华（qwen 激励硬编码 + flash 结构性护栏 + pro 回溯与冷却），去 pro 评价器与 qwen 自动验收边界；顺序按 C→E1→A→B→D。
**否决线**：pro 的 SQL DSL 原子事务、execution_context 跨 agent 注入、分析者当评价器；qwen 的 WM 绑任务生命周期、常驻 daemon 后门、押金前置——六项明确否决。

**对 pro 最狠的批评**：它的 DSL 原子事务和 execution_context 注入两处都自相矛盾（前者违反六状态机、后者与自己的 WM 会话生命周期冲突）——治理先于能力是对的，但它的两个能力载体一个都立不住，说明它把"治理意识"用在了正确的顺序上、却把"载体选择"用在了错误的地方。
**对 qwen 最狠的批评**：它洞察最锋利（任务即持久单位、转录前置、激励挂钩）却把 A 的落点钉在"任务生命周期"上——为了 B 的自洽牺牲了 A 的真实用途，分析者综合阶段恰好没有 RAM 可用；洞察正确不代表落点正确。
