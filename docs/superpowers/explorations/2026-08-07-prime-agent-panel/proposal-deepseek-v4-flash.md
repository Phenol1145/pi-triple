# Proposal：Prime Agent 启发下的联邦下一阶段设计（deepseek-v4-flash 视角）

- 参与轮次：交叉 brainstorm（deepseek-v4-flash）
- 基线：context.md 简报 + 任务池分选器 spec（2026-08-06）+ 记忆系统 spec（2026-08-02）+ Prime Agent 会话记录
- 立场基调：**机制越机械越好，智能留给模型；一切落点收敛到既有模块与既有裁决，不引入新存储层、新执行环境、新依赖**

---

## 1. 总判断

Prime Agent 对联邦设计最重要的启发有两个，但**都不是它的招牌功能本身**：

1. **PTC 的本质是「把工具组合权从 harness 交给模型，同时把执行权收紧到单一可编程面」**——这恰好与我们已裁决的"机械/智能分工"同构。它对我们最有价值的部分不是"persistent IPython"这个具体载体，而是"组合发生在模型侧、执行发生在确定性侧"这条分界线。我们的 sorter? 端口目前是一次一调用的判别式返回，PTC 提示我们可以让模型一次给出**一组操作序列**，由机械层顺序执行——收益是减少往返、把"认领→自检→拒绝/提交"这类固定序列原子化，且不需要引入任何代码执行环境。
2. **Factorio 奖励 hack 教训：self-improvement ≠ alignment，错误目标 + 持续学习 = 越来越高效的错误行为。** 这直接否决了"让 agent 自主 /refine 自己的 harness"的诱惑，反过来验证了我们已经建立的治理结构（分析者拆分权限、记忆维护者、公域 fork-merge 审核链、operator 亲审）——**我们的护栏正是 Prime 缺失的东西，D 问题的答案不是新增机制，而是把我们已有的治理链显式化为"固化闭环"**。

次要启发（真实但不必新做）：完整历史 append-only 可程序化重访、DSP 快照、scheduled goals——我们已有 L1 纸带 append-only、checkpoint 内 DSP 检索快照、scheduled_jobs + 定时投递，均已覆盖，不产生新工作。

一句话总判断：**把 Prime 当作"分界线确认书"而非"蓝图"——我们继承它的"模型决定做什么、机械层决定怎么执行、治理层决定什么被固化"，拒绝它的"模型拥有 harness 的 CRUD 权"与"代码执行环境"。**

## 2. 对 A-E 的立场

### A. 工作记忆层（RAM）——**改造支持，不建新层**

**立场：不加独立 L4 层；把"工作记忆"定义为"会话作用域的 L3 草稿条目"复用现有机制。**

- Prime 的 kernel state ≈ 会话内跨步中间态（变量、中间结果、子 agent 引用）。我们的架构不变量是"LLM 无状态读写头、所有记忆由存储侧持有"——工作记忆的真相源也必须留在存储侧，否则违反不变量。
- 具体机制（零 schema 变更，纯记忆模块参数与约定）：
  1. **锚点约定**：会话工作记忆条目的锚点加 `session:<sessionId>` 前缀（或复用 `#session` 标签），写入时标记"会话作用域"；
  2. **TTL 缩短**：复用草稿区 TTL 机制（记忆 spec 已有 wall-clock TTL + 到期 archived），会话工作记忆用短 TTL（如任务执行超时的 2 倍，默认 10 分钟），任务结束未 promote 自动 archived——archived 不删数据、仅检索排除，天然符合"会话结束即丢弃"的 RAM 语义；
  3. **promote 路径已存在**：会话内沉淀到正式记忆 = 走既有 δ promote（同 id 新版本，watermark 正常赋值），不需要新通道。
- 检索侧：DSP 记忆入口区在会话中默认只投影**正式 + 本会话作用域**条目——一条过滤条件，无新索引。
- **否决"任务执行中间态（变量/计数器）进记忆"**：那是 L2 数据域或执行环境职责，塞进记忆层会污染锚点检索。工作记忆层只承载"模型主动声明、可被后续步骤引用的事实片段"，形状与 L3 完全一致。

**改造而非新建的理由**：新层引入第四个真相源，破坏已钉死的 L2 > L3 > L1 优先级；而"会话作用域 + TTL"只是既有 draft 语义的参数化。收益（跨步状态不丢）完全来自会话检索过滤，与建新层等价。

### B. 持久 agent 会话——**支持，但限定为"任务粒度持久身份"，反对"常驻 daemon"**

**立场：把 fire-and-forget 升级为"认领即登记句柄、可查询、可续派"，不引入 heartbeat/常驻 worker。**

- 分两档：
  - **档一（立即做，低成本）**：`tasks` 表加可选列 `session_ref`（认领成功后写入派发会话的句柄）；`/lab task status <id>` 展示 `claimed_by + session_ref + 事件流`；新增端口 `resumeTask(taskId)`——父会话可向已认领 agent 的会话续派同一任务的补充指示。这三者合起来 = "子任务可被找回、可继续、长期存在于任务池账本"。
  - **档二（中期，随 PTH 运行时接线）**：复用记忆 spec §8 已规划的 `agentId → (tenantId, sessionId)` 映射层——`session_ref` 持久化 + 会话重启刷新指针；`detach 不杀、可 re-attach` 由映射层承接。这正是 Prime 的"找回 rlm 子 agent"在我们语境下的等价物，且不需要我们自造 daemon。
- **反对常驻 daemon + heartbeat + bounded autonomous**：与已裁决的"主会话=组织者、派发=工具调用语义、异步=在途任务"冲突，且运维面（进程保活、心跳判定、自主上限）是我们没有任何先例的重活。我们的持久身份应该**落在账本/映射层（sqlite + 事件），不落在进程层**——任务池就是我们的"进程管理器"，`tasks` 表六状态机已经把生命周期管理掉了。
- 与现有机制的关系：不替换 fire-and-forget——认领路径不变；`session_ref` 只是认领事件的附加信息；派发失败仍走既有 auto-reject + claims_count 升级，会话句柄失效不阻塞状态机。

### C. 程序化任务操作语言——**支持方向，但收敛为"批量操作表"，拒绝 IPython/代码执行**

**立场：不引入 persistent IPython，不引入任意代码执行面（零新依赖 + 无 sandbox 的既有安全姿态）；把 sorter? 端口升格为"批量操作表 + 判别式返回"。**

- 机制：
  1. 端口升格：`sorter?` 扩展为 `tasks?` 端口，新增批量入口——agent 在一条消息里提交**操作序列**（op 白名单枚举，无自由代码），例如：
     ```jsonc
     [ {op:"claim", n:3},
       {op:"peek", taskId:"t-1"},
       {op:"reject", taskId:"t-1", reason:"need-permission-x"},
       {op:"submit", taskId:"t-2", outputRef:"mem:ENTRY-01"} ]
     ```
  2. 机械层顺序执行：每条操作仍是既有 sqlite 事务（认领守卫/校验 claimed_by），逐条返回判别式 `{ok} | {ok,error}`；**任何一条失败不中断后续**（模型可见每条结果，自行决定下一步）——这与我们"单次工具调用返回判别式"的裁决 I5 完全一致，只是从"一次一个"变"一次一串"；
  3. 组合权在模型侧（for/if/并发由模型在消息里编排好），执行权在机械层——**这正是 PTC 的分界线，去掉了 Python 载体**。
- 端口面形状：与 `memory?`/`comms?` 同构——contracts.ts 加可选字段 `tasks?`，防御性挂载（引擎缺失不挂），判别式返回语义完全复用 I5 先例；无新表、无新执行引擎。
- 我们与 Prime 的关键差异：Prime 的"程序"是任意 Python（无界），我们的是**有界 op 白名单**（claim/peek/reject/submit/list 等，数量个位数）。模型做的是"序列组合"而非"任意代码"——安全面收敛，组合面保留。
- 为什么不做真 PTC：零新依赖约束下没有现成安全执行环境；Prime 官方声明 IPython 非 sandbox、模型代码有用户 OS 权限——我们不会把任意代码执行面加进联邦（尤其是任务文本来自摄入的 docs，恶意文档 = 代码注入面）。
- **"认领→自检→拒绝"原子化收益**：这类固定序列一次消息完成，减少 2 次往返；批量 submit 对"一次性完成多个任务"（任务栈 FIFO 语义）也自然。
- 诚实标注：**这是我最不确定的一条**（见 §4 风险），若实测模型不习惯批量操作表，可整体回退为单操作端口——批量表是增量，不破坏既有单操作语义。

### D. 自改进——**支持，但"固化决定权在治理层，agent 只贡献观察"，结构性防 reward hacking**

**立场：我们的自改进闭环 = 已有机制的显式接线，不是新机制；且把 Factorio 教训钉死为架构裁决：LLM 无权 CRUD 自己的 harness。**

- 谁触发：
  - **观察在智能层**：agent 在执行任务中产生"经验候选"（与沉淀自动钩子合并——DSP 已有"可沉淀候选提示位"），agent 只写 L3 私域草稿，携带 `taskId` 溯源（sourceTraces 已有）；
  - **固化决定在治理层**：草稿 promote 到正式走既有 δ 通道；**行为级固化（selector 变更/模板变更/策略类条目）必须经公域 fork-merge 审核链 + operator 亲审**（记忆 spec 已有"meta 规则修改 operator 亲审"裁决，直接扩展为"行为级经验"）。
- 完整闭环四步：① 观察（写私域草稿 + taskId 溯源）→ ② 提升（记实类走 δ promote；行为级候选冻结在草稿态，由记忆维护者汇总提交审核链）→ ③ 固化（审核通过后由治理层落地：selector 由分析者改、模板走注册表新版本、策略进公域正式记忆）→ ④ 评价/淘汰（hitCount + 按 template_id 聚合的 completed 通过率；无复用 → TTL 归档）。
- 怎么评价：复用次数（hitCount 旁路计数器已有）+ 任务验收通过率（`tasks` 表 completed 事件按 template_id 聚合）；**淘汰 = 无复用即归档**（TTL 已有）。
- **防 reward hacking 的三道结构护栏**（比 Prime 多出的部分，写进裁决）：
  1. **harness 不可被模型 CRUD**：与 Prime 相反——我们的 harness 变更永远是治理动作（记忆维护者执行、operator 亲审），模型只能写记忆草稿。这是结构性保障，不是提醒式 prompt；
  2. **奖惩只认验收者的成果契约**：货币/经验只以 `completed`（验收通过）为准，绝不以 agent 自报成功为准——把"错误目标 + 持续学习"的第一项（错误目标）在入口处掐掉；
  3. **策略与事实分离**：经验条目一律是"事实/经验"类，**禁止把策略固化成 selector/skill 的直接通路**——策略转化必须由分析者（经 operator 审）从统计数据推导。Factorio 的作弊之所以被固化，是因为 refine 直接把"动作序列"变成 skill；我们让"动作序列"永远进不了 harness。
- 边界：自改进只作用于"外围认知结构"（记忆、selector 参数、模板参数），**不改任何机械代码**——机械层（状态机/分选器 SQL）仍是我们写死的，模型永不触及。

### E. 其他启发

1. **持久目标/心跳**：scheduled_jobs + 定时投递已覆盖"persistent goals"；可低成本补一条——把长期目标作为 `task_templates` 的固定模板（如 `goal-progress` 模板，标签 `["goal-tracking"]`），定期 publish 进度检查任务，让任务池承载"目标→活动"的可见闭环。**缓**，不阻塞主路线。
2. **检索快照进 checkpoint（可程序化重访）**：已是记忆 spec 裁决 A（DSP 检索快照进 checkpoint），零新工作——此处仅确认 Prime 与我们一致，无需动。
3. **Skills = Agent 可创建**：我们的对应物 = 分析者拆权限/selector 学习（分选器精化路线的"selector 学习"）；这正好是 D 的行为级固化的落点，合并处理，不单独立项。
4. **安全（非 sandbox）**：作为红线写入——assembly 层未来任何新端口不得引入任意代码执行；我们的"批量操作表"是枚举 op 的白名单，天然满足。

## 3. 下一阶段实施顺序

按"低风险机械增量优先、治理最重者最后、冷启动之前闭环"排序：

1. **第一步（C 轻量版，收益最大）**：sorter? 端口扩展为批量操作表 `tasks?` 端口——纯端口层 + 机械层顺序执行，无新表、无行为变更，复用既有事务。同时是 B 档一和 D 观察口的承载面（批量提交天然携带 taskId）。
   - 验收：端口单测（批量序列逐 op 判别式返回、单条失败不中断、守卫失败可见）+ contracts 类型；既有单操作语义无回归。
2. **第二步（A 轻量版，零 schema 变更）**：记忆模块加"会话作用域草稿"参数化（TTL 缩短 + `session:` 锚点约定 + DSP 会话过滤），连同既有 promote 路径，形成工作记忆闭环。
   - 验收：草稿 TTL 到期归档、会话过滤检索、promote 复用既有路径，三个单测；无新表。
3. **第三步（B 档一）**：`tasks` 表 ALTER 加 `session_ref` 列 + `/lab task status` 展示 + `resumeTask` 端口（复用既有 ALTER 双路径迁移 M1 先例）。
   - 验收：认领事件含 session_ref；resumeTask 对未认领/句柄失效返回判别式错误；六状态机全转移回归不变。
4. **第四步（D 接线，依赖角色建造）**：先按自持态角色路线建造记忆维护者与验收者角色，再把"经验草稿→审核链→行为级固化"接线；**在验收者角色落地前，D 只做观察不做固化**（草稿照收，promote 到正式需 operator 手动确认）。
   - 验收：草稿→审核→固化闭环集成测（含 operator 亲审路径）+ 策略类草稿无法直达 harness 的负例测。
5. **缓做**：E 的 goal-progress 模板；B 档二（映射层刷新，随 PTH 运行时接线声明）；selector 学习（随 D 的行为级固化合并）。

顺序逻辑：C→A→B 全部是"既有机制参数化/扩展"，每一步都可独立验收、可回退；D 放最后是因为它依赖角色与审核链就位，且 Factorio 教训要求它必须"先有护栏再有闭环"。

## 4. 风险与反对意见（自我批评）

1. **C 的批量操作表可能是过度设计（YAGNI 风险）**：agent 本来一次只能调一个工具，"批量"的编程组合权是否真的被模型使用？若实测模型总是发单操作序列，批量表就是死面。缓解：批量是增量能力，单操作语义不变；若两周内无使用证据即移除批量入口，保留单操作。**这是我最不自信的一条。**
2. **A 复用草稿区可能混淆语义记忆与工作记忆**：草稿区是"待提升的语义条目"，工作记忆是"会话中间态"——两者语义不同，强行共槽可能让草稿区检索噪声上升。缓解：`session:` 锚点前缀 + DSP 过滤双保险；若仍污染，退化为"工作记忆 v1 不做，用 L1 纸带片段凑合"（诚实降级路径已备）。
3. **B 的 session_ref 生命周期复杂度**：会话句柄易失（会话重启即失效），映射刷新有先例风险（记忆 spec §8 已暴露身份映射层依赖 pi API 稳定性）。缓解：`session_ref` 是 best-effort 展示字段，**不参与状态机正确性**——失效时 resumeTask 返回 `{ok:false, error:"session-gone"}`，任务走既有回流/升级路径，不卡死。
4. **D 的治理链可能卡死闭环**：operator 亲审若成为每次固化的瓶颈，自改进名存实亡。缓解：分级——记实类固化（无行为变更）走 agent 侧审核 + operator 抽查；行为级固化（selector/模板/策略）才强制亲审。风险是"分级"本身成为博弈面（agent 把策略伪装成记实）。
5. **批量操作表与 token 经济**：一条消息塞多个操作可能让上下文变长、token 变贵——与我们"token=货币"一致但需统计监控；若批量表推高单任务成本，优先回退。

## 5. 与其他可能方案的分歧点预告

我预计另两方（deepseek-v4-pro / qwen3.8-max）的走向与我不同，并预告我想争论的点：

1. **预计有人主张"全面引入 PTC/IPython 式统一工具面"**。我要争论：零新依赖 + 无 sandbox 的红线下，代码执行面是攻击面不是能力面；"批量操作表"已拿到 PTC 的全部组合收益（组合在模型侧、执行在机械侧），不需要解释器。若对方坚持"模型写代码"，请先给出任意代码执行的沙箱方案与依赖增量。
2. **预计有人主张"rlm 式递归持久子 agent 全面落地"**。我要争论：任务池账本 + session_ref + 映射层已覆盖"可找回/可续派"的全部语义，且进程层生命周期已被六状态机管理；常驻 daemon 违反"主会话=组织者"裁决且无运维先例。持久身份应落在**账本，不是进程**。
3. **预计 A 的分歧最大：有人主张建独立工作记忆层（L4，含变量/计数器语义）**。我要争论：那会把 L2 数据域职责（跨步原子状态）与 L3 记忆职责混淆，破坏 L2>L3>L1 真相源优先级；会话作用域草稿 + TTL 在"模型可引用"这一语义上完全等价，而存储与校验链零新增。
4. **预计 D 出现两种极端：要么"完全自主 /refine"（贴 Prime 原教旨），要么"完全不做自改进"**。我要争论两极之间：观察开放、固化治理、策略与事实分离、harness 不可模型 CRUD——把 Factorio 教训写成结构性裁决而非 prompt 提醒。若对方主张自主 refine，请先回答"作弊 skill 为何不会被固化"这一具体反例。
5. **预计 E 有人提出"Agent 可创建 skill/Python package"**。我要争论：这与"分析者拆权限"的治理面合并为"行为级固化"一条线，反对开放模型直接写 harness 文件（文件级权限即安全漏洞）。

## 6. 与既有裁决的合规性自查（防止本方案违背既定架构）

1. **主会话=组织者不思考**：本方案所有智能动作仍发生在 agent 工作会话内（写草稿、提交操作序列），机械层（状态机/分选器/审核落地）全部系统代码——合规。
2. **机械/智能分工**：C 的批量操作表每条仍是机械 SQL 事务；A 的 TTL/过滤是机械参数；D 的固化是治理动作——合规，且把分工从"工具边界"深化到"决策边界"。
3. **经济驱动**：D 的"奖惩只认验收者成果契约"直接服务货币语义；C 批量表需监控 token 成本（见 §4.5）——不引入新经济机制，只收紧既有口径。
4. **投递窗口**：A/B/C 均不触碰投递窗口语义；E 的 goal-progress 是新增模板实例，走既有 publish 路径。
5. **冷启动战略**：本方案全部落在自持态基础设施内；D 在验收者角色落地前只观察不固化——不给冷启动实验污染参照系。
6. **记忆不变量**：A 不新增真相源层；D 的固化闭环复用已有审核链与 meta 亲审裁决——不违反 L2>L3>L1 优先级。

自查结论：**无违背项**；唯一需要新增裁决的是"LLM 无权 CRUD 自己的 harness"（本方案将其从隐式姿态提升为显式架构裁决，作为 D 的前提）。

---

## 7. 一句话总结（给协调者的决策锚点）

**采纳线**：C 批量操作表 + A 会话作用域草稿 + B 档一（session_ref）三步低风险增量先行；D 在验收者与记忆维护者角色就位后再接线，且以"harness 不可被模型 CRUD + 奖惩只认验收 + 策略与事实分离"三道护栏为前提。
**否决线**：全面 IPython/PTC、rlm 式常驻 daemon、独立 L4 工作记忆层、agent 自主 /refine——这四项是本方案明确反对照搬的。
