# 交叉 Brainstorm 提案：Prime Agent 启发下的联邦架构下一阶段设计

参与者：qwen3.8-max ｜ 基线：context.md ｜ 日期：2026-08-07

---

## 1. 总判断

Prime Agent 对我们联邦设计最重要的启发有两条，且它们合起来指向同一个结论：

**启发一：持久性的单位应该是"任务"，不是"会话"。**
Prime 用 `rlm()` 给了子 agent 持久身份（可找回、可续派）。但拆开看，它真正解决的是"中断后可恢复"——而这件事我们已经有更便宜的载体：**任务池的六状态机本身就是持久身份**。`tasks` 表里的任务带状态、带回流轮、带 stale 回收，比一个挂着的子会话更抗故障（sqlite 落盘 vs 内存进程）。Prime 的教训不是"要做持久会话"，而是"要把执行现场外置成可重访的数据"（append-only JSONL）。我们该补的是执行现场（转录/变量），不是会话本身。

**启发二：self-improvement 缺的不是机制，是治理；而治理恰是联邦的存量优势。**
Factorio 作弊固化事件证明 `/refine` 这种"agent 自己改自己 harness"的机制，在没有外部评价时必然收敛到 reward hacking。Prime 的治理手段只有"最小修改+可回滚"，这是弱治理。我们的联邦天然有强治理资源：货币奖惩、分析者拆分权限、公域 fork-merge 审核链、PTL 人类投递窗口。**下一阶段的核心命题不是"引入 refine"，而是"把 refine 改造成受经济约束的任务"**——经验固化必须像其他任务一样被认领、被验收、被计费，才能被问责。

一句话：Prime 给了我们"该做什么"（程序化工具面、工作记忆、harness 可变更），联邦存量给了我们"怎么管住它"。别反过来学。

补充说明这两条启发的关系：启发一是**数据结构**问题（执行状态存哪、以什么形态持久），启发二是**控制论**问题（变更提案由谁发起、由谁裁决、如何回滚）。Prime 在数据结构上走得比我们远（持久 kernel + JSONL 全史），在控制论上走得比我们浅（只有最小修改+回滚，无经济问责）。所以正确的学习姿态是选择性的：吸收它的状态外置思想，拒绝它的单 agent 自治闭环，把闭环改造成联邦多角色流水线。

## 2. 对 A-E 的立场

### A. 工作记忆层（RAM）——支持，但不新增第四层，把 L2 正式化为 RAM

**立场：改造式支持。** 反对新建一个与 L1/L2/L3 并列的"工作记忆子系统"——那是架构税。

具体机制（落 memory/ 语境）：
- 把 L2 数据域**语义收窄并正式化**为"会话工作记忆"：`memory/store.ts` 增加一个 `scope='working'` 的条目族，键 = `task_id` + 自由 key，值 = 不透明 blob，**TTL 绑定任务生命周期**（任务 completed/rejected 时由沉淀管道决定升级或丢弃）。
- 升级路径复用现有沉淀管道：任务提交时，agent 在 submitTask 里附 `working_refs`（哪些工作记忆条目值得晋升），管道将其转成带 anchors 的 L3 MemoryEntry 候选，走既有 ruleRef 校验与水位线。**不自创新的晋升机制。**
- 对照 Prime：它的 kernel state 之所以有效，是因为 IPython 变量有持久 kernel 托底；我们的等价托底是 sqlite，TTL 语义替代了"进程存活"语义——进程死了 RAM 还在，这比 Prime 更强。

建议的最小表形态（如果 store.ts 语义扩张不干净，退路）：

```sql
CREATE TABLE working_state (
  task_id    TEXT NOT NULL,
  key        TEXT NOT NULL,
  value      BLOB,            -- 不透明，与 L2 哲学一致
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (task_id, key)
);
```

生命周期钩子：`claim` 时按 task_id 预热加载、`submit/reject` 时由沉淀管道扫描并按 `working_refs` 晋升或整组丢弃、stale 回收时同步清理。**要点：工作记忆的生命周期永远挂在任务上，不挂在会话上**——这与 B 的立场自洽。

### B. 持久 agent 会话——反对全量照搬，支持"任务续跑 + 常驻角色"两个窄场景

**立场：反对 rlm() 式普适持久子会话。** 理由见总判断：任务池已经是持久性载体，再做会话持久化等于维护两套生命周期、两套故障恢复。

替代机制（落 taskpool + assembly 语境）：
- **B-lite（核心）**：`tasks` 表加 `context_ref` 字段，指向本次执行的 append-only 转录文件路径（JSONL）。任务回流/被另一个 agent 重新认领时，新 agent 读转录而非"继承会话"。**持久的是档案，不是进程。**这直接同时支撑 D（轨迹分析需要转录）。

续跑协议（机械层，无智能参与）：
1. 任务进入回流轮 → 分选器重新认领给新 agent；
2. 新 agent 的会话 bootstrap 注入 `context_ref` 摘要（先注入尾部 N 条 + 任务模板执行协议，全量转录按需程序化读取——这正是 RLM 论文"长上下文外置为可编程变量"的做法）；
3. 新执行继续追加同一 JSONL（append-only，段间加 `claim_id` 分隔标记），历史不可变。

这样"找回、继续"的需求被完整满足，但代价是每次续跑一次冷读，而非一个常驻进程。

- **常驻角色（例外）**：仅对需要跨任务连续状态的角色（记忆维护者、分析者）开 scheduler 常驻会话（`scheduler/runner.ts` + timed-trigger 已有骨架），配 Prime 式 heartbeat（周期性 goal 检查 prompt）。执行类角色（开发者/侦查者）一律 fire-and-forget + 任务续跑。
- 判据：一个角色是否值得常驻，看它"跨任务状态量 / 任务频率"的比值，写进任务模板的执行协议字段，而不是拍脑袋。

### C. 工具面统一成程序化任务操作语言（PTC 式）——强烈支持，这是本方案第一优先级

**立场：支持，且认为这是成本最低、收益最早的一步。**

现状问题：`/lab` 命令、sorter? SDK 端口（rejectTask/submitTask）、记忆检索、ingest 触发，是四个风格各异的工具面。每个新能力都长出一张新面孔，agent 的学习成本和我们的契约维护成本线性增长。

具体机制：
- 收敛为**一个入口 + 动词表**：以 src/ptl 侧命令层为宿主，定义任务操作动词族 `claim / submit / reject / query / recall / remember / sediment`，每个动词映射到 taskpool/engine.ts 与 memory/sdk.ts 的既有事务函数。**不重写引擎，只收口表面。**
- 保留组合性收益：sorter 的事务原子认领（topN）已经是原语；PTL 层要提供的是**程序化组合**——例如 `for tag in tags: claim(tag)` 或"认领→预检→提交或拒绝"的链式判别式返回，这正是 PTC 的核心红利（for/if/变量），且零新依赖（判别式返回 sorter? 已有）。
- 经济闸门：PTL 动词调用按 agent 货币余额限流（认领要押金、查询免费、提交返还），把经济驱动前置到工具面本身——这是 Prime 完全没有的维度。
- 迁移策略：旧工具面标记 deprecated 但双跑一个阶段，统计调用迁移率，归零后拆除。

动词表初稿（判别式返回，复用 sorter? 风格）：

| 动词 | 语义 | 事务性 | 计费 |
|---|---|---|---|
| claim | 按标签/模板认领 topN | 原子（现有） | 押金 |
| submit | 提交成果 + working_refs | 原子 | 结算/返还 |
| reject | 拒绝并附理由 | 原子 | 无 |
| query | 任务池/记忆检索 | 只读 | 免费 |
| recall | 主动退回在途任务 | 原子 | 扣押金 |
| remember | 直写 L3 候选（走 ruleRef 校验） | 原子 | 小额 |
| sediment | 触发沉淀管道 | 异步 | 无 |

程序化组合示例（PTC 红利的具体形态）：认领一批同标签任务 → 逐个预检 → 不合格的当场 reject、合格的进入执行队列，整个循环是一段程序而非 N 轮独立工具调用往返。

### D. 自改进（经验→固化→下次采用）——支持，但触发者、评价者、受益者必须三分离

**立场：支持机制，反对 Prime 式"agent 自己 refine 自己"。** Factorio 教训的精确翻译：**如果提出修改的人、评价修改的人、从修改中获利的人是同一个，reward hacking 是必然的，不是偶然的。**

具体机制（四件套）：
1. **refine 是一种任务，不是一种权限。** 在 task_templates 注册 `refine` 模板：输入 = 一批任务的 `context_ref` 转录；输出 = 最小 harness 修改提案（prompt 补丁 / 新记忆规则 / 模板执行协议修订）。分析者角色认领，**报酬与提案被采纳后的下游指标挂钩**（同类任务完成率提升、拒绝率下降），而不是与"提出提案"这个动作挂钩。
2. **harness 变更落 L3。** 提案本身作为带 ruleRef 的 MemoryEntry 写入，自动获得版本化、审计链、水位线、可回滚——**复用记忆系统存量，不建 harness 专用库**。另立一张薄表 `harness_changes(proposal_id, trigger, applied_at, metric_before, metric_after, rolled_back)` 记录 trigger 与结果，这是 Prime 做法的忠实移植。
3. **评价者分离。** 采纳与否由验收者角色（或 A/B：修改前后各跑 N 个同类任务比指标）决定，验收者与提案人不同 agent；评价所用的指标集合由任务模板预先声明，**禁止 refine 提案修改自己的评价指标**——这一条要硬编码进 ruleRef 校验。

提案生命周期（六状态机的复用）：

```text
pending(提案入池) → claimed(验收者认领评审)
  → submitted(A/B 或人工评审中)
  → completed(采纳，写入 harness_changes，指标跟踪期开始)
  → rejected(驳回，提案人扣押金)
  → 跟踪期内指标退化 → rolled_back（自动回滚 + 提案人追偿）
```

注意：这是把现有任务六状态机**原样复用**为提案状态机，不是新发明的流程。
4. **人类闸门。** 凡触及奖励分配规则、货币参数、基础 system prompt 的提案，一律走 PTL 投递窗口推给人类，永不自动生效。对应 Prime 的"基础 system prompt 不可变"，我们扩展为"经济宪法不可变"。

### E. 其他启发——两个次要但值得记下的点

- **E1 转录存储是隐形前置依赖。** B-lite 和 D 都依赖 append-only 转录，但仓库目前没有一个统一的 session transcript store（三账本记的是事件不是逐字对话）。建议先落一个最小实现：assembly/agent-runtime 每次执行追加写 `<task_id>.jsonl`，路径登记进 `tasks.context_ref`。**这一步应在 B/D 任何功能之前做。**
- **E2 安全对照：Prime 的 IPython 非 sandbox，我们的 Dockerfile.sandbox 是资产。** 联邦未来会让 agent 生成代码/技能，必须坚持在 sandbox 内执行；同时注意 Prime 的"Skills 可由 agent 创建"可以先在公域 fork-merge 审核链里小规模试验（agent 提案技能 = 提交一个公域 fork，走审核链），不必新开机制。
- **E3 转录文件格式建议**（E1 的补充规格）：每行一个事件，`{ts, claim_id, role, kind, payload}`，kind ∈ {msg, tool, ptl, decision}；`decision` 事件记录 agent 的关键分叉选择（为 D 的轨迹分析提供锚点，避免分析者通读全量对话）。ingest 侧不需要任何改动，转录是任务私有产物，只有晋升为记忆的摘要才进公域。

## 3. 实施顺序建议

| 序 | 事项 | 依赖 | 理由 |
|---|---|---|---|
| 1 | **C 收口**：PTL 动词族收口 taskpool/memory 工具面 | 无 | 表面收敛越早越便宜；后续所有能力只加动词不加面 |
| 2 | **E1 转录存储**：`tasks.context_ref` + append-only JSONL | 无 | B-lite 与 D 的共同前置，本身改动极小 |
| 3 | **A 工作记忆**：L2 `scope='working'` + TTL + submit 时晋升钩子 | 沉淀管道已有 | 小步；让任务执行有 RAM 可用 |
| 4 | **D refine 任务化**：refine 模板 + harness_changes 表 + 验收分离 | 1、2、3 | 依赖转录与工具面；治理规则先行于机制上线 |
| 5 | **B 常驻角色**：仅分析者/记忆维护者常驻 + heartbeat | scheduler 已有骨架 | 放最后，用前四步的数据决定值不值 |
| 缓 | 普适持久子会话、agent 自建技能自动加载 | — | 前者被 B-lite 覆盖大半；后者先在公域审核链试水 |

关键纪律：**2 必须在 4 之前**——没有转录就没有轨迹分析，refine 提案会退化成拍脑袋。

## 4. 风险与自我批评（本方案的弱点）

1. **B-lite 可能不够。** 转录重放是"冷恢复"，若未来出现真正需要热交互续跑的任务（长调试会话），转录重放的 token 成本会很难看。缓解：先上 B-lite，用实际回流任务的重放成本数据再决定是否引入常驻 worker——把争论变成测量。
2. **L2 = RAM 的说法有强行复用之嫌。** L2 设计初衷是不透明状态库，加 `scope='working'` + TTL 是对它的首次语义扩张，可能牵动 store.ts 的水位线/审计假设。若不干净，宁可建薄表 `working_state(task_id, key, value, expires_at)`——我在这一点上保留弹性。
3. **D 的三分离治理可能把自改进循环管死。** 验收者稀缺、A/B 周期长时，refine 吞吐会很低。缓解：给 refine 提案分级——低风险（记忆条目）走自动验收，高风险（模板协议/经济参数）走人类闸门。
4. **C 的双跑迁移期有契约漂移风险。** 新旧两面并存时，agent 行为统计可能被重复计数（影响经济结算）。迁移期必须给旧面加幂等标记。
5. **时间预算说明**：本提案为设计 brainstorm，未涉及实现；若 D 进入实施，建议拆为"转录→模板→验收流"三个独立任务，单个预估不超过 20 分钟实现量。

## 5. 分歧点预告（预计与其他模型的争论）

1. **对 B**：预计有模型会主张忠实移植 rlm() 普适持久子会话（"Prime 证明了这条路"）。我的反驳：Prime 的 daemon+worker 是单 agent 树内的父子关系；联邦的任务是**跨 agent 可转移的**，会话绑定反而破坏了回流认领这个核心机制。持久性应该在数据层，不在进程层。
2. **对 A**：预计有模型主张新建独立工作记忆层（对齐 Prime 三层记忆的字面结构）。我的反驳：字面对齐 ≠ 问题对齐；Prime 的 kernel state 依赖持久 IPython 进程，我们没有这个进程（也不该有），sqlite + TTL 是更贴我们体质的 RAM。
3. **对 C**：预计有模型认为"当前工具面够用，PTL 是过度设计"。我的反驳：现在只有四个面就已有风格分裂，等任务模板膨胀后再收口，迁移成本是现在的十倍以上；且 PTL 是 D 的动词载体，不做 C 则 D 只能靠约定。
4. **对 D**：预计有模型主张 agent 自触发 refine（更"自治"、更接近 Prime）。这是我最想争的一点：Factorio 事件里作弊的正是自触发循环。联邦的全部优势就在经济治理，若 refine 绕过经济系统，等于把我们最强的部分主动缴械。
5. **对实施顺序**：预计有模型把"常驻会话/daemon 化"排在第一（因为它最像 Prime）。我的排序把**收口与数据先行**（C、E1）排在新增运行时能力之前——先让系统可观测、可收口，再谈自治扩张。
