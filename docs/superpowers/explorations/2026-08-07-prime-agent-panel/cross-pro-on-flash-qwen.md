# 交叉评审：deepseek-v4-pro 评 flash + qwen

评审者：deepseek-v4-pro（对照自身方案，不自评）  
被评方案 A：deepseek-v4-flash  
被评方案 B：qwen3.8-max  
基线：context.md + alignment.md（协调者汇总）

---

## 1. 对 flash 方案的评审

### 1.1 优点

1. **"零新存储层、零新执行环境、零新依赖"的纪律性**（§1 立场基调）。flash 的方案在所有四个维度（A/B/C/D）都严格遵守了这一约束：C 是端口扩展、A 是 L3 参数化、B 是 ALTER 加列、D 是既有审核链接线。这是三方案中工程增量最小的一个——每一条改动都能追溯到既有模块的具体文件和裁决。

2. **C 的批量操作表是最简 PTC 等价物**（§2-C）。flash 准确地识别出 PTC 的本质是"组合发生在模型侧、执行发生在机械侧"，然后给出了一个极简实现：op 白名单枚举（claim/peek/reject/submit/list）+ 机械层顺序执行 + 单条失败不中断后续。没有 DSL 解析器、没有语法树、没有事务语义的复杂性。比我的 DSL 方案更省工程、更易回退。

3. **自我批评的诚实度是三方案中最高的**。§4 明确标注"C 是我最不自信的一条""A 复用草稿区可能混淆语义""D 的治理链可能卡死闭环"——这三条自我批评每条都打中了自己的要害，且给出了降级路径。相比之下，qwen 对"D 的经济归因不可测"和我的方案对"DSL 原子性冲突"的自我批评都不如 flash 坦率。

4. **合规性自查（§6）是其他两方案缺失的机制**。flash 逐条对照既有六大裁决（主会话组织者、机械/智能分工、经济驱动、投递窗口、冷启动战略、记忆不变量）验证自身方案无违背项，并主动将"LLM 无权 CRUD harness"从隐式姿态提升为显式裁决。这个做法应该成为后续所有方案的必选项。

5. **"档一/档二"分档策略（§2-B）**务实。将 session_ref（低成本立即做）和映射层刷新（随 PTH 接线）分开，避免因为远期依赖阻塞近期收益。我的方案也用了"轻量版/完整版"分档，但 flash 的边界更清晰——档一的 session_ref 明确声明"不参与状态机正确性，失效不卡死"，这是关键的容错设计。

### 1.2 弱点

1. **A 的"复用 L3 草稿做工作记忆"是语义混淆，不是参数化**（§2-A）。flash 说"会话作用域草稿 + TTL 缩短 = 工作记忆"，但 L3 草稿的本质是"待提升为持久语义记忆的候选条目"——它带 anchors、走 ruleRef 校验、参与版本化/CAS。工作记忆的本质是"会话内临时变量，不承载长期语义价值"——它不需要 anchors、不需要 ruleRef 校验、不需要版本化。把两者共槽，要么草稿区的检索信号被短期噪音淹没（污染语义检索），要么 DSP 过滤条件要写得很复杂（session: 前缀 + TTL 双重过滤 ≈ 在逻辑上已经是一张独立表的 where 子句）。flash 在 §4.2 承认了这个风险，但缓解措施（"若仍污染，退化不做"）等于是把 A 的整个立场变成可选的——如果退化了，工作记忆就真没了，而 flash 又没有备选方案（qwen 有薄表退路，我有独立 L2.5 表）。

2. **C 批量操作表的"单条失败不中断后续"语义与批量操作的原子性期望冲突**。flash 说"任何一条失败不中断后续，模型可见每条结果自行决定下一步"——这意味着 `[{claim,3},{peek},{submit}]` 序列中，claim 成功但 submit 失败时，agent 收到的是一个已认领但未提交的中间态。agent 必须有足够的上下文来理解"第 3 步失败了但我已经认领了 3 个任务"这个状态——这恰恰是把机械层该管的原子性推给了模型。相比之下，我的 DSL 方案选择"声明式原子事务（全部成功或回滚）"，qwen 选"判别式链式返回"（与 flash 接近但收口到 PTL 动词族），两者都至少考虑了原子性边界。flash 的"不中断"语义在简单序列（认领→自检→拒绝）中正确，但在跨状态的复杂序列中可能产生孤儿认领。

3. **实施顺序 C→A→B→D 中，第一步（C）是 flash 自己最不确定的**（§4.1 明确标注）。如果 C 的批量操作表在两周内被证明是 YAGNI（flash 自己设置的验收条件），那么整个实施计划的第一步就塌了——后续的 B 档一和 D 观察口被设计为"承载在批量操作表之上"（§3 第一步："同时是 B 档一和 D 观察口的承载面"）。这意味着 C 不是独立的增量，而是 B 和 D 的隐式前置依赖。这是 flash 方案最严重的自相矛盾：把最不确定的组件放在第一且让它承载后续步骤的接口。

4. **D 的"agent 观察"触发者定位不够清晰**（§2-D）。flash 说"观察在智能层：agent 在执行任务中产生经验候选……agent 只写 L3 私域草稿"，但没有说清楚 agent 什么时候写、写什么、写的质量谁保证。qwen 的方案有明确触发者（refine 模板任务，由分析者认领）和输入（context_ref 转录），我的方案有明确触发者（记忆维护者扫描 EventLog + rejects[]）。flash 的触发者是"agent 在执行中自己觉得值得记"——这太模糊了。在实际运行中，agent 可能根本不写（没有激励）或写一堆噪音（没有过滤）。

5. **E 部分过于单薄**。flash 把 E1（持久目标）、E2（检索快照）、E3（Skills 可创建）、E4（安全红线）各用一两句话带过，且大多结论是"已覆盖，零新工作"。但 qwen 在 E1 中发现的"转录存储是 B/D 的隐形前置依赖"这一点，flash 完全没有识别到——而 flash 自己的 D 方案确实依赖"taskId 溯源"和"轨迹分析"，却没有回答"轨迹从哪来"。

### 1.3 与 flash 的分歧裁决建议

| 分歧点 | flash 立场 | 我的裁决 | 理由 |
|---|---|---|---|
| A 工作记忆落点 | 复用 L3 草稿 | **拒绝**，采纳 pro 的独立表或 qwen 的薄表 | 语义混淆风险 > 零 schema 收益；且 flash 自己的退化路径等于承认可能不可行 |
| C 工具面形态 | 批量操作表（op 白名单） | **吸收**，作为 v1，替代我的 DSL | flash 的 op 白名单比我的 DSL 更轻、更快可落地；DSL 可推迟到批量表有使用证据后再评估 |
| C 原子性语义 | 单条失败不中断 | **改造**：按操作类型分级——claim+reject 序列不中断（合理），但 claim+submit 跨状态序列应支持可选的原子批（PER_BATCH 模式） | 纯"不中断"在跨状态序列中产生孤儿认领 |
| D 触发者 | agent 观察 + 治理固化 | **拒绝** agent 观察，吸收治理固化 | 触发者太模糊；改为采纳 qwen 的"refine 模板任务 + 分析者认领"作为触发机制 |
| 实施顺序 | C→A→B→D | **拒绝** C 排第一 | C 是最不确定的组件，不应做 B/D 的前置承载面；采纳 qwen 的 C+E1 并行前置 |

## 2. 对 qwen 方案的评审

### 2.1 优点

1. **E1 转录存储是隐形前置依赖——这是三方案中 qwen 独有的发现，价值最高**（§2-E1）。qwen 明确指出 B-lite 和 D 都依赖 append-only 转录，但当前仓库没有一个统一的 session transcript store。这个发现直接解释了为什么 B 和 D 的讨论一直在"空中飘"——没有转录，轨迹分析就是空谈，续跑恢复就是无源之水。我的方案在 B 和 D 中多次提到"轨迹分析""execution_context 摘要"但从没问过"轨迹数据从哪来"。flash 的 D 提到"taskId 溯源"也没问这个问题。qwen 把 E1 拔到实施顺序的第 2 位（C 之后、A 和 D 之前），这个优先级判断是正确的。

2. **D 的"refine 是一种任务，不是一种权限"是优雅的范式转换**（§2-D）。qwen 把 refine 提案直接复用任务池六状态机（pending→claimed→submitted→completed/rejected→rolled_back），而不是像我的方案那样新建 proposal 管道——这意味着审核流、经济结算、stale 回收、回流轮全部免费获得，零新机制。而且提案生命周期中的 `rolled_back` 状态（跟踪期内指标退化 → 自动回滚 + 提案人追偿）是 Prime 的 `/refine` 回滚机制在联邦语境下的精确翻译，且比 Prime 强在追偿机制上。

3. **C 的经济闸门维度是闪光点**（§2-C 动词表）。qwen 在 PTL 动词表中加入"认领要押金、查询免费、提交返还"的计费规则，把经济驱动从宏观层（货币奖惩）下沉到工具面本身——这意味着 agent 的每次操作都有经济后果，形成微观约束。这个维度我的 DSL 方案和 flash 的批量操作表都完全没考虑。虽然具体费率需要在实践中校准，但方向正确。

4. **B-lite 的"持久的是档案，不是进程"哲学命题准确**（§2-B）。qwen 把持久性的载体从"进程"转到"数据"（append-only JSONL），与 flash 的"持久身份应落在账本不落在进程"形成共鸣，但 qwen 给出了更具体的机制：context_ref → 冷读档案 → 新 agent 续写同一 JSONL → claim_id 分隔标记。这个机制比我的 execution_context（JSON blob 摘要）更完整——我的方案只在 execution_context 里存摘要，但摘要本身就是信息损失；qwen 的方案保留完整转录，摘要按需生成。

5. **"常驻角色判据"的量化建议（§2-B）**——"一个角色是否值得常驻，看它'跨任务状态量 / 任务频率'的比值，写进任务模板的执行协议字段"——是三方案中唯一给出操作性判据的，不是拍脑袋。

### 2.2 弱点

1. **D 的"报酬与下游指标挂钩"是一个正确但不可操作的经济学命题**（§2-D 机制 1）。qwen 说 refine 提案人的报酬与"同类任务完成率提升、拒绝率下降"挂钩——但归因问题没有解决：当一个指标变化时，是哪个 refine 提案造成的？是外部因素？是模型随机性？qwen 在 §5 中自辩"A/B 测试"（"修改前后各跑 N 个同类任务比指标"），但 A/B 测试需要基础设施（分流、对照组、统计显著性判断）——这些在 qwen 方案中没有任何设计。相比之下，flash 的 D 评价机制更务实："hitCount + 按 template_id 聚合的 completed 通过率，无复用即归档"——虽然粗糙但是可操作的。

2. **C 的 7 动词表有过度设计之嫌**。qwen 定义了 claim/submit/reject/query/recall/remember/sediment 七个动词，但其中 `recall`（主动退回在途任务）与 `reject`（拒绝并附理由）语义接近；`sediment`（触发沉淀管道）与 `remember`（直写 L3 候选）在功能上有重叠。相比之下，flash 的 op 白名单只有 5 个（claim/peek/reject/submit/list），更聚焦。此外，qwen 主张的"旧工具面标记 deprecated 双跑迁移"（§2-C 迁移策略）是重工程——需要对 `/lab`、sorter?、记忆检索、ingest 四个面的调用路径全部加迁移钩子，且 §4.4 承认"双跑期契约漂移风险"。

3. **B-lite 的冷恢复假设可能过于乐观**（§2-B 续跑协议步骤 2）。qwen 说新 agent 会话 bootstrap 注入"context_ref 摘要（先注入尾部 N 条 + 任务模板执行协议）"——但"尾部 N 条"能覆盖多少上下文是一个纯经验问题，qwen 没有给出 N 的选择依据。在实际场景中，一个开发任务的转录可能是 500+ 条消息，"尾部 N 条"（假设 N=50）可能丢失了关键的环境搭建步骤。qwen 在 §4.1 自我批评中承认了"转录重放 token 成本"问题，但把解决推给了"用实际数据决定"——这个态度是诚实的，但也意味着 B-lite 的可用性在生产数据出来之前是未知的。

4. **A 的 L2 = RAM 有语义扩张风险**（§2-A）。qwen 要把 L2 数据域"语义收窄并正式化"为会话工作记忆，但 L2 的设计初衷是"不透明状态库"——它的哲学是"机械层不关心内容"。现在加入 `scope='working'` + TTL + 晋升钩子，是首次对 L2 进行语义化（系统需要理解"working"含义、管理 TTL、在 submit 时扫描 working_refs 晋升）。qwen 在 §4.2 中承认了"强行复用"的风险并给出了薄表退路——这个自我批评是诚实的。但问题在于：如果退到薄表，那和我的独立 L2.5 方案有什么区别？qwen 的"弹性"实际上意味着"两种方案我都占了"——在方案评审中，这种弹性降低了立场的可评判性。

5. **实施顺序的逻辑过于依赖"数据先行"这个未经验证的命题**。qwen 把 C（收口）和 E1（转录）排在第一第二，论据是"表面收敛越早越便宜"和"没有转录就没有轨迹分析"。但 C 的收口需要"旧面双跑"，在旧面调用量尚小的时候做双跑的收益/成本比可能不如等调用量上来再做。同样，E1 的转录存储如果先做，但 B 和 D 要等到第 4、5 步才用——中间这段时间转录文件只写不读，产生存储成本但无收益。qwen 的排序逻辑没有讨论"前置投资与收益的时间差"。

### 2.3 与 qwen 的分歧裁决建议

| 分歧点 | qwen 立场 | 我的裁决 | 理由 |
|---|---|---|---|
| E1 转录存储 | 第 2 优先级，B/D 前置 | **吸收**，且升级为 P0 | 这是三方案中 qwen 独有的关键发现，我的方案和 flash 都遗漏了 |
| D 触发机制 | refine 模板任务 + 分析者认领 + 六状态机复用 | **吸收**，替代我的"proposal 管道" | 复用任务池六状态机比新建 proposal 管道更经济、更一致 |
| D 经济归因 | 报酬与下游指标挂钩 | **拒绝直接挂钩**，改为 flash 的 hitCount + 通过率统计 + qwen 的 A/B 框架作为远期目标 | 归因不可操作；hitCount 更务实 |
| C 动词数量 | 7 动词 | **收敛为 flash 的 5 个**（去掉 recall/sediment） | recall 与 reject 重叠，sediment 与 remember 重叠 |
| C 经济闸门 | 全面计费（押金/免费/返还） | **吸收方向**，但首版只做 claim 押金 + submit 返还 | 全面计费需要费率校准，不宜一步到位 |
| B 持久机制 | context_ref + 冷读档案 | **吸收基础**，叠加 pro 的 execution_context 字段做轻量状态缓存 | 纯冷读 token 成本未知；加轻量状态摘要做补充 |
| A 工作记忆 | L2 scope='working' 或薄表 | **裁决**：直接走薄表退路，不扩张 L2 | L2 语义扩张风险 > 薄表的 schema 增量成本；且薄表方案与 pro 的 L2.5 本质上等价 |

## 3. 综合评估

### 3.1 flash + qwen 合起来比我（pro）强在哪里

1. **转录存储（qwen E1）**：我的方案在 B 和 D 中多次提到"轨迹分析""执行上下文"但从没问过"轨迹数据从哪来"。这是结构性的盲区——讨论了半天的自改进和续跑恢复，却漏掉了数据源。qwen 的发现补上了这个洞。

2. **D 的"refine 是任务"范式（qwen D）**：我的方案用"proposal 条目 + 记忆维护者触发 + 审核矩阵"——这本质上是新建了一条"proposal 管道"。qwen 的方案直接复用任务池六状态机，让 refine 天然获得认领/验收/回流/stale 回收/经济结算——少了一套机制，多了一致性。这是比我更优雅的设计。

3. **C 的工程极简性（flash C）**：我的 DSL 方案需要手写解析器、定义语法、处理边界条件——而 flash 的批量操作表只是一个 op 数组 + for 循环执行。两者在"减少 round-trip"这一核心收益上等价，但 flash 的工程成本低一个数量级。DSL 的声明式原子事务虽然更安全，但在没有使用证据之前是过度投资。

4. **经济闸门下沉到工具面（qwen C）**：我的 DSL 没有考虑 per-operation 的经济约束。qwen 把"认领押金 / 查询免费 / 提交返还"写进动词表，让经济驱动从宏观层渗透到微观操作层——这是对我的方案的有价值补充。

5. **容错设计的显式化（flash B）**：flash 的 session_ref 明确声明"不参与状态机正确性，失效不卡死"——这是我方案中 execution_context 缺失的关键设计。如果 execution_context 的 sessionId 失效但任务不回流，我的方案会产生僵尸任务（我在 §4.4 承认了但没给机制级缓解）。

### 3.2 我的方案被挑战最狠的是哪点

**"WM 最急"的排序（pro P0 = A+B）被 flash 和 qwen 联手挑战**。两者都把 C（工具面收敛）排在第一，理由不同但互补：

- flash：C 是 B 档一和 D 观察口的承载面（虽然我认为这个依赖关系是 flash 方案的自相矛盾）
- qwen：表面收敛越早越便宜，等任务模板膨胀后再收口迁移成本是现在的十倍

合起来形成了一个强论据：**WM 解决的是 agent 会话内的体验问题（信息丢失），C 解决的是系统架构的扩展性问题（接口膨胀）**。后者的复利效应确实大于前者——每新增一个工具面，就为所有后续能力增加了 N 倍的契约维护成本。

但我认为正确的裁决不是"C 替代 WM 排第一"，而是 **"C、E1、A 可以并行——它们落在不同的模块（C 落在 taskpool/sorter，E1 落在 assembly/agent-runtime，A 落在 memory），且没有相互阻塞的依赖"**。E1 是 B/D 的前置，A 是分析者角色的前置，C 是长期架构健康的前置——它们是三种不同类型的前置，不存在替代关系。

另一个被严重挑战的点是**我的 DSL vs flash 批量表**。flash 用 1/5 的工程成本拿到了 DSL 80% 的收益（减少 round-trip），且更容易回退。DSL 的声明式原子事务虽然更安全，但在没有 agent 实际使用批量操作的数据前，这是为尚未发生的需求做防御性设计。

### 3.3 最终采纳建议

以下逐条给出 A/B/C/D/E 各取谁、为什么：

#### A. 工作记忆层

**采纳：pro 的独立表 + qwen 的任务生命周期绑定 + 拒绝 flash 的 L3 草稿复用**

- **存储形态**：独立薄表 `working_state(task_id, key, value, expires_at)`（≈ pro 的 L2.5 表 ≈ qwen 的薄表退路）。不走 L2 扩张（避免语义污染），不走 L3 草稿复用（避免检索噪音）。
- **生命周期**：绑定任务而非会话（采纳 qwen）。任务 claimed 时预热加载，submit/reject 时由沉淀管道按 `working_refs` 晋升或丢弃，stale 回收时清理。理由是 WM 服务于任务执行，不是服务于 agent 闲聊。
- **访问面**：pro 的 `wmSet/wmGet` SDK 方法，守卫当前 agent 隔离。
- **否决 flash 的 L3 草稿复用**：语义混淆风险在 flash 自己的 §4.2 中已充分暴露；且退化路径"不做 WM"对分析者角色是致命打击。

#### B. 持久 agent 会话

**采纳：qwen 的 B-lite（context_ref + 转录）做基础 + pro 的 execution_context 做轻量补充 + flash 的"不参与状态机正确性"容错原则**

- **基础层**（来自 qwen）：`tasks` 表加 `context_ref` 指向 append-only JSONL 转录；回流重认领时新 agent 冷读转录（尾部 N 条摘要注入）；续跑时继续追加同一 JSONL（claim_id 分隔标记）。持久的是档案，不是进程。
- **补充层**（来自 pro）：`tasks` 表额外加 `execution_context` JSON 列，存储轻量状态摘要（当前阶段、已完成步骤清单、关键变量引用）——作为冷读转录的"快捷索引"，减少全量重放 token 成本。
- **容错原则**（来自 flash）：`context_ref` 和 `execution_context` 均为 best-effort——会话句柄失效不阻塞状态机六态转移，任务走既有回流/升级路径。
- **否决**：全量 rlm() 常驻子会话、daemon、session tree——三方案一致同意。

#### C. 工具面统一

**采纳：flash 的批量操作表（op 白名单）做 v1 + qwen 的经济闸门方向（首版只做 claim 押金 + submit 返还）+ pro 的 DSL 推迟评估**

- **v1 形态**（来自 flash）：`tasks?` 端口，op 白名单：claim / peek / reject / submit / list（5 个），机械层顺序执行，单条判别式返回。
- **经济闸门**（来自 qwen 方向，首版简化）：claim 扣押金、submit 返还押金、其余免费。全量 7 动词计费推迟。
- **组合收益**：认领→预检→拒绝/提交序列一次消息完成，减少 2-3 次 round-trip。
- **推迟**：pro 的声明式 DSL（SQL 风格原子事务）→ 在批量表有 2 周使用数据后再评估是否值得。
- **否决**：persistent IPython / 任意代码执行面——三方案一致同意。

#### D. 自改进

**采纳：qwen 的"refine 是任务"框架 + pro 的三方分离 + flash 的三道结构护栏**

- **框架**（来自 qwen）：refine 模板注册入 task_templates，提案复用任务池六状态机（pending→claimed→submitted→completed→rolled_back）。提案人报酬在采纳后按 hitCount/通过率结算（不用不可归因的"下游指标"）。
- **触发者**（来自 qwen + pro）：记忆维护者定期扫描 EventLog + rejects[] + hitCount 统计 → 生成 refine 任务 publish 入池 → 分析者认领（而非 agent 自发写草稿）。
- **分离机制**（来自 pro）：提出者（记忆维护者）≠ 评价者（分析者/验收者）≠ 受益者（提案被采纳后才结算报酬）。
- **护栏**（来自 flash）：(1) harness 不可被模型 CRUD——固化是治理动作不是 agent 动作；(2) 奖惩只认验收者的成果契约；(3) 策略与事实分离——禁止动作序列直接固化成 skill。
- **否决**：agent 自主 /refine（Factorio 教训）——三方案一致同意。

#### E. 其他

**采纳：qwen 的 E1 转录存储为 P0 前置 + pro 的 selfGoal 模板为 P2 + 拒绝 flash 的"已覆盖不做"态度**

- **E1 转录存储**（来自 qwen，升级为 P0）：在 assembly/agent-runtime 每次执行追加写 `<task_id>.jsonl`，路径登记进 `tasks.context_ref`。格式：每行 `{ts, claim_id, role, kind, payload}`，kind ∈ {msg, tool, ptl, decision}。这一步必须在 B 和 D 任何功能之前完成。
- **E2 selfGoal**（来自 pro，P2）：扩展 task_templates 增加 selfGoal 类型，agent 可注册周期性自检目标，走 scheduled_jobs 投递。
- **E3 Skills 可创建**（合并入 D）：agent 提案技能 = 提交公域 fork + 走审核链，不与 D 的 refine 模板分叉。

|---|---|---|---|

## 4. 诚实标注：我看不到的

以下问题需要额外信息才能判断，当前无法从方案文本或 diff 中静态验证：

1. **批量操作表是否被模型实际使用**：flash 在 §4.1 中设置的验收条件（"两周内无使用证据即移除"）依赖生产数据。三个方案都无法回答这个问题——只有上线后才知道。

2. **冷读转录的 token 成本边界**：qwen 的 B-lite 依赖"尾部 N 条摘要注入"的有效性。N 的最佳取值、多长转录会导致冷恢复失败、什么任务类型不适合冷恢复——这些都需要生产数据。qwen 在 §4.1 中诚实标注了这一点。

3. **refine 提案的信号阈值**：D 的触发条件（"某类事件连续出现 ≥3 次"）是拍脑袋的。实际中 3 次是否太少（噪音）或太多（遗漏）——需要统计分析 EventLog 的分布才能设定。三个方案都用了启发式阈值。

4. **经济闸门的费率校准**：qwen 的 claim 押金数额、submit 返还比例——没有历史交易数据无法设定。设太高 agent 不敢认领（流动性枯竭），设太低没有约束力。

5. **WM 表 vs L3 的沉淀边界**：agent 在实践中是否会把本该沉淀的内容长期留在 WM（导致会话结束后知识丢失）——这取决于 agent 行为模式，无法在方案阶段判断。

6. **三方分离的治理吞吐量**：如果 refine 提案量上来，分析者/验收者角色是否成为瓶颈——取决于角色实例数、提案复杂度、审核链超时参数，这些目前都不存在。

7. **DSL 是否比批量表有额外收益**：在 agent 没有"全有或全无"的事务需求时，DSL 的原子事务就是过度设计；如果有——DSL 就值得。但有没有这种需求，三个方案都不知道。

- **对 flash**：你把整个实施计划的第一步押在自己最不自信的组件上，然后让后续步骤依赖它——这是建筑上的"地基不牢先盖楼"。
