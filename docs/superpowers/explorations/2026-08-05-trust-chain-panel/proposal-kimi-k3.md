# 信任链形式化提案（kimi-k3-256k · Round 1）

## 1. 形式化定义

**信任链不是一条"链"，而是一个以命题为节点、以担保为有向边的有限有向无环图（DAG），外加一个封闭的元信任对象集合。**

精确定义。给定对象域 O（数据、代码、记忆条目、计算结果——§7 "任何数据（含代码）"）：

- **信任主张（claim）**：c = (o, P)，其中 o ∈ O，P 是关于 o 的可判定命题（"o 可解析"／"o 内容可信"／"o 结果可信"）。**信任链是按命题索引的**——同一对象对不同命题有不同的链（§7.1 三语境即三个 P）。
- **担保关系（warrant）**：w = (c_target, c_source, e)，意为"主张 c_source 为 c_target 的可靠性作出承诺"，e 为**证据**（使该担保可被第三方审计的数据载荷）。
- **元信任对象（meta-trust objects）**：封闭集合 M——自证／无需担保的根。M 是**枚举出来的有限集合，不是涌现的**。
- **信任链结构**：TC(P) = (C, W, M)，C 为主张集，W ⊆ C × C × Evidence 为担保边集（边方向：被担保 → 担保），要求：
  1. **无环**：W 上不存在有向环（循环担保不构成 grounding）；
  2. **收敛**：从任意 c ∈ C 出发沿 W 必在有限步内到达以 M 中对象为担保方的主张，且 M 对象自身无出边。

**声明式（§7.2 已决）的形式化含义**：信任链是一个**记录函数** τ: Claim → WarrantRecord（可审计记录的生成义务），而非**前置谓词**（生效条件）。链的"成立"是**审计时可判定的谓词**，在质疑／结算／回退时按需求值，不在数据产生或构件生效时强制求值。这是本提案与"信任链 = 部署闸门"解释的根本分野。

## 2. 结构与验证语义

### 2.1 组成元素

| 元素 | 定义 | 骨架锚定 |
|---|---|---|
| **被担保者** | 主张 c = (o, P) 中的对象 o | 记忆条目／构件／计算结果 |
| **担保者** | **必须是一个节点**（§1.1）——担保不是数据的属性，而是主体的责任行为 | 担保消耗担保者的权利（见 §3.2） |
| **证据 e** | 使担保可审计的数据：引用指针（traceId/transitionSeq/watermark）、规则标识（rule_id + version）、执行记录、哈希链指针 | sourceTraces／L1 纸带／rule 链（已实施） |
| **元信任对象 M** | 封闭根集。**本提案的核心论断：三种语境的 M 收敛于同一类对象——设计者预置、系统内不可修改的机制／介质**（与宪法 A4 同构，见 §4） | base 语法／append-only 介质／市场闭环机制 |

### 2.2 验证语义——"链成立"分三级

声明式属性要求区分**结构存在**与**语义有效**：

- **L1 链完整（structural presence）**：主张附有不缺环节的 τ 记录——每个非根主张至少一条出边，图在 M 收敛。L1 失败 = **断链**或**悬根**（终止于 M 之外）。
- **L2 链有效（evidential validity）**：审计时对每条边求值——证据良构、担保者在担保时持有相应权限、证据指向的对象仍可复原（watermark 未失效、rule 版本仍可解析）。
- **L3 链当前（currency）**：所有担保未被撤销、未被后续证据推翻（见 §5 撤销问题）。

"链成立"默认指 L1∧L2；L3 是时间敏感的，只能对某一时刻断言。**环 = 结构性无效**（违反 DAG 公理），在 L1 即拒绝。

## 3. 与联邦骨架的关系

### 3.1 与责任⇄权利（A2）：担保是有代价的责任行为

**担保边不是免费元数据。**发出担保 = 担保者承担"若被担保命题为假，我负责"的责任（A2 责任侧）；该责任由经济机制执行配对（§6 锚定：economy 是 A2 执行器）——虚假担保 → elo 损失／结算罚没／额度后果。这把信任链**焊进**骨架公理体系而非外挂：信任链的每条边都是一条微型的"责任⇄权利"承诺。由此推出：**无质押的担保是无效担保**——担保者必须有可损失的东西（elo／额度），匿名无责主体不能作担保者。

### 3.2 与法律（§1.7）：法律规定信任策略

类比"图法律必备回退触发条款"（§1.8），本提案主张：**图法律必备信任条款**——治理节点立法时必须规定：本图内哪些命题 P 要求强制 τ 记录（记录义务）、本图承认的元信任对象集合（M 的下层投影）、最大链深。法律依然是指导性流程约束（自然语言为主），信任条款是其结构性组成部分。

### 3.3 与构件部署（§4.2）：存在性检查 ≠ 强制验证

§4.2 写"构件 → 信任链验证 → 填槽生效"，§7.2 裁决"不在构件生效前强制验证"。本提案的调和：**填槽生效的前置条件是 L1 链完整（记录存在且收敛到 M），L2/L3 求值推迟到审计**。即：构件上传时必须**附上**担保记录（谁担保、证据指针），但部署管线不**求值**证据真伪。这既满足 §4.2 的"验证"字面（结构性校验），又满足 §7.2 的"不强制拦截"（语义性校验缺席）。此解释是否正确，列入 §5 分歧点。

### 3.4 与治理／回退节点：审计权与信任崩塌

- **治理节点**：A4 治理权限已含"审计"——审计的具体内容即对子图内信任链做 L2/L3 求值。治理是计算任务（A3），**审计消耗治理者额度**——这给出"谁为验证付费"的答案：验证成本由治理者的治理额度承担，是治理责任的一部分。
- **回退节点**：**系统性信任崩塌**（某图内大量链 L2 失效、或发现悬根/伪担保）= "图无法自处理的问题"的一个实例 → 触发回退透传（§1.8 push 模式，建议作为图法律可追加的触发项，T 由图法律定）。
- **宪法同构**：M 的合法性来源与宪法完全相同——**设计者预置、系统内不可修改**。这打破"信任的顶层自指"，正如 A4 打破"治理权限的顶层自指"。信任链不是新的顶层机制，而是宪法自证模式的第三次复用（第一次：法律；第二次：治理/回退节点骨架自带 §3.3；第三次：元信任对象）。

## 4. 实例化模式

**统一论断**：三种语境的元信任对象看似各异，实则同属一类——**设计者预置的机制／介质**。信任链在所有语境中收敛到"骨架自带的、系统内不可修改的东西"。

### ① 记忆条目可解析（P₁ = "条目可解析"）

- **构造**：τ(entry, P₁) = { 生成该条目时约束它的 rule (rule_id, version) }；rule 的可解析性由其上层 rule 担保，沿 rule 链上行 → **base（语言体系四层根的 EBNF/语法基底）**。
- **元信任对象**：**base 语法本身**——其可解析性由定义自证（语法定义了"可解析"的语义，命题 P₁ 对 base 无意义／恒真）。
- **L2 求值**：审计时以 rule_id+version 复原规则并重跑解析——可机械判定，成本有界。

### ② 记忆信息可信（P₂ = "条目描述的信息可信"）

- **构造**：τ(entry, P₂) = { 引用链边：本条目的内容主张由哪些先前条目担保 } + { append-only 证据：sourceTraces (traceId, transitionSeq) + watermark（§memory-spec 钉死语义）}。
- **对 §7.1 表格的修正（对抗性指出）**：§7.1 将"引用链 + append-only"列为元信任对象——**这在概念上不成立**：引用链是链本身（担保边集），不能同时是自己的根。真正的根是：**append-only 介质中的直接观测记录**（L1 纸带上的原始事件）——纸带条目是观测事实（"某时某 agent 说了某话"），其真实性由**介质的 append-only 性质**担保，而 append-only 是机制属性（设计者预置），即元信任对象 = **append-only 介质 + 其上的直接观测**。
- **无环保证**：要求担保边只能指向 **watermark 严格更小**的条目（时间拓扑序）——由 watermark 单调性把 DAG 公理降为可机械校验的不等式。
- **注意**：append-only 保证"记录未被篡改"，不保证"记录的内容为真"——②的担保强度天然弱于①，链只能担保"信息来源可溯且未被事后修改"。这是声明式定位下的诚实边界。

### ③ 计算结果可信（P₃ = "节点的计算结果可信"）——元信任对象提案

**构造**：每个结果 r 附 τ(r, P₃) = { 产出节点 id；输入主张集（各输入的信任链——递归）；构件身份（该结果由哪个填槽构件的哪个版本产出——空位绑定记录）；执行记录（traceId / checkpoint seq）}。

**元信任对象 = 市场闭环的评审-结算机制本身（execute → review → settle 相位通路）**。论证：

1. 结果可信的自然担保者是**另一个节点的独立复核**——而骨架里"复核"不是临时安排，是**机制性相位通路**：市场相位结构（§6 锚定：market-runner execute → review → settle）中的 review 相位节点，就是执行结果的制度化担保者。结果沿相位通路流动，每经过一个相位即获得该相位节点的担保边。
2. 担保链收敛于 **settle（结算记录）**：结算完成的记录 = 评审担保已被经济机制确认（担保者的 elo/credit 已按结算规则承付）。再往上，担保链终止于**市场闭环机制本身**——它是系统计算图的固定拓扑（骨架）、宪法保护、设计者预置、系统内不可修改（A4）。
3. 于是三种语境统一：**M = { base 语法；append-only 介质；市场闭环机制 } ——全部是"设计者预置的机制/介质"**。信任链的元信任层与宪法层重合，这是联邦骨架只有一个"自证之根"（设计者/PTL）的必然推论。
4. 补充担保模式（承认但不作为根）：**冗余执行**（多节点独立重算并比对）与**执行者质押自认**（产出者以 elo/额度质押）——二者都是普通担保边，最终仍需经评审/结算收敛到机制根。质押自认单独不构成根：自认若无质押是无效担保（§3.1），质押的兑现恰恰依赖结算机制——所以还是收敛到机制。

## 5. 关键分歧点自陈（Round 2 预备）

1. **DAG vs 线性链**：我坚持信任链是 DAG（一个结果有多个输入主张、一条目多源担保——sourceTraces 本身就是数组）。若有模型主张"链"字面上必须是线性的，我认为它无法覆盖多源溯源的已实施事实（memory-spec sourceTraces: Array）。
2. **§4.2 与 §7.2 的张力**："填槽生效需信任链验证" vs "不强制验证"。我的调和是 L1 存在性前置 + L2/L3 审计推迟。但**这可以被攻击为变相强制**——L1 检查毕竟拦在生效前。若会谈裁决"连记录存在性也不前置"，则 §4.2 需改写为"生效后限期补齐担保记录"。**这是最需要设计者裁决的点。**
3. **③ 元信任对象 = 机制是否循环**：我用"市场闭环机制"作根，而该机制本身的正确性由设计者断言——这是否只是把信任问题推给 PTL 而没有真正收敛？我的辩护：这正是宪法的处境（A4），骨架已接受"设计者预置"为唯一合法之根；不接受此同构的模型需给出**不落在系统外**的根，我认为不存在（任何系统内根都需要担保，违反 M 定义）。
4. **担保的经济成本与审计付费**：每条担保边是否消耗额度（A3 式）？审计成本谁付？我主张"审计 = 治理任务，治理者额度支付"，但这意味着**信任链密度受治理者额度制约**——富裕图信任可验证、贫困图信任只能靠声明，这是否可接受？
5. **撤销与 append-only 的矛盾**：担保事后被发现虚假时，记录不可删（append-only），只能追加"撤销记录"——链的 L3 语义因此是时间切片的（"t 时刻链成立"）。②语境的 append-only 与信任的可撤销性如何共存，预计有分歧。
6. **M 的封闭性**：我主张 M 枚举封闭且宪法级固定；对立立场可能是"图法律可声明本图额外的元信任对象"（如某组织自认其内部公证节点为根）。我认为后者必然引入悬根风险，但承认它更接近联邦的多元现实。
