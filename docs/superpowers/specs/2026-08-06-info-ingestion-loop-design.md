# 信息摄入循环 v1 设计（联邦落地第一里程碑）

- **日期**：2026-08-06
- **状态**：设计（brainstorming 定稿，待用户审阅）
- **定位**：联邦愿景的第一个落地里程碑。联邦存在的意义 = 体系持续摄入信息并整理成易于访问的格式；本设计交付这个循环的最小完整切片。
- **前序依赖（已就绪）**：记忆系统（`extensions/agent-lab/src/memory/`，MemoryStore/Pipeline/锚点检索/hitCount，123 测试全绿）；调度器三模式 + `/lab scheduler dispatch` 命令；timed-trigger 定时任务表；装配层 sdk.memory 挂载（MemoryHost.attachSdk）

---

## 1. 背景：联邦架构语境

本设计来自联邦架构讨论的收敛结论，以下语境约束设计决策：

1. **联邦的意义 = 信息资产积累**。任务经济、分选器、货币都是手段；系统持续摄入信息 → 整理成结构化可检索形态 → agent 低成本访问，联邦才"越用越值钱"。
2. **文档层 = 文件夹+文档，怎么方便怎么放**。摄入不预设结构；组织智能来自角色，不来自管道。
3. **记忆管理者是专职角色**。语义分解、倒排索引、引用化降重、对抗性审核冲突信息是该角色的工作（= 任务池中的维护任务），不是自动管道的硬编码逻辑。v1 只落地其第一个任务类型：语义分解。
4. **任务投递窗口**：任务进入系统的入口，两种投递策略——**定时投递**（timed-trigger 机制）与 **PTL 投递**（人工经 `/lab scheduler dispatch`）。窗口开闭语义（池空关窗）属于未来任务池+分选器，v1 不碰。
5. **检索统一走记忆访问**（`sdk.memory.retrieve` 锚点检索），不开第二条检索通道。
6. **主会话 = 组织者**：真正的思考由（同步/异步）协作单元完成；记忆维护任务的执行者是 workloop agent，主会话侧只负责投递与回收。

## 2. 目标与非目标

### 目标（v1 = 全闭环薄切片）

1. **摄入管道**（新代码主体）：仓库 `docs/` → 扫描 → 路径推导标签 → 指针条目写入记忆系统（机械、确定性、幂等、增量）；加周期流接线（§5）构成全部新代码
2. **检索与热度**：复用 `sdk.memory.retrieve` + hitCount，验证可访问性
3. **任务投递窗口打通**：定时投递（注册 timed-trigger job）+ PTL 投递（现有命令）两条路都能把维护任务送进调度器
4. **记忆管理者的第一个任务类型**："语义分解"任务被 workloop agent 接取执行，产出原子条目回写记忆系统

**机械/智能分工（语义钉死）**：摄入是机械行为——系统定时器或 PTL 直接调用管道函数，**不经 agent、不耗 token**；任务投递窗口只承载 agent 任务（语义分解等）。摄入产出增量后自动为变更文档派发语义分解任务——这是机械层与智能层的交接点。

### 非目标（明确不做）

- ⛔ 任务池 + 分选器（正则+标签拉取）——未来联邦机制
- ⛔ 货币挂钩（摄入/维护任务的赏金结算）——等货币设计定稿
- ⛔ LLM 摘要/提炼——v1 摘要用机械规则（标题+首段）
- ⛔ 引用化降重、冲突对抗审核、倒排索引的精化——记忆管理者角色后续任务类型
- ⛔ **记忆所有权划分**（分析者职责：按思考方向/角色划分记忆域的归属）——后续演进，已入路线
- ⛔ 向量检索（记忆系统设计已明确不做）
- ⛔ 改动任何既有文件的行为语义

## 3. 架构总览

```
┌─ 任务投递窗口 ──────────────────────────────────┐
│  定时投递：timed-trigger job → dispatch           │
│           （caller=timed-trigger → 自动 weighted）│
│  PTL 投递：/lab scheduler dispatch（人工）        │
└──────┬───────────────────────────────────────────┘
       ↓ 语义分解维护任务（agent 任务）
┌─ 摄入管道（新建：extensions/agent-lab/src/ingest/）┐
│  触发：系统定时器 / PTL 直调（机械行为，不经 agent） │
│  docs/ 扫描 → 路径推导标签 → 指针条目写入          │
│  产出增量 → 自动派发该文档的语义分解任务            │
└──────┬────────────────────────────────────────────┘
       ↓ sdk.memory.write（校验/幂等/溯源/事件 既有机制）
┌─ 记忆系统（既有，零改动）────────────────────────┐
│  指针条目（摄入产出）+ 原子条目（语义分解产出）     │
│  sdk.memory.retrieve = 唯一检索入口；hitCount=热度 │
└──────┬────────────────────────────────────────────┘
       ↓ workloop agent 接取"语义分解"任务（sdk.memory 已挂载）
  读文档 → 拆原子事实 → sdk.memory.write 回写
```

**文档层零拷贝**：`docs/` 本身即文档层。摄入不复制、不改写原文档；索引与条目是旁路产物。

## 4. 摄入管道（新代码细节）

位置：`extensions/agent-lab/src/ingest/`（与 memory/ 同级；零新增依赖、node:test、import 后缀 `.ts`）

| 文件 | 职责 |
|---|---|
| `source.ts` | 源适配器接口：`list(): SourceDoc[]`，`SourceDoc = { relPath, title, firstPara, contentHash }`。v1 一个实现；接口形状源无关（外部源/会话源未来加适配器） |
| `docs-source.ts` | 仓库 docs 适配器：递归扫描 `*.md`；title = 首个 `# ` 标题（缺省 = 文件名）；firstPara = 标题后首个非空段落（截断上限 500 字符）；contentHash = sha256(全文) |
| `tags.ts` | 纯函数标签推导（§4.1） |
| `pipeline.ts` | 编排：遍历源文档 → 按 relPath 查已有指针条目 → contentHash 相同跳过 / 不同写新版本 / 无条目新建；返回摘要 `{ scanned, created, updated, skipped }` |

### 4.1 标签推导规则（纯路径，零维护）

输入 = 相对 docs/ 根的路径。规则：

1. 每级目录段原样成为标签（`superpowers/specs/...` → `superpowers`, `specs`）
2. 文件名去扩展名、去日期前缀（`^\d{4}-\d{2}-\d{2}-`）成为标签（`2026-08-02-memory-system-design.md` → `memory-system-design`）
3. docs/ 根下直属文件（无目录段）→ 仅文件名标签
4. 不做大小写折叠、不做分词、不做同义归并——标签精化是记忆管理者后续工作
5. 锚点非空不变量：规则保证至少产出 1 个标签（文件名标签恒存在）

### 4.2 指针条目形态

```
MemoryEntry {
  id:         确定性派生（relPath → sha256 → UUID 形态字符串）——同文档恒同 id
  kind:       "fact"
  anchors:    §4.1 推导标签
  content:    "# <title>\n\n<firstPara>\n\n源: <relPath>"
  ruleRef:    摄入模块初始化时经规则 bootstrap 通道注册的构造规则条目
              （描述指针条目格式；MemoryEntry 校验链要求 ruleRef 有效）
  status:     "official"（机械产出、结构确定，不走草稿区）
  idempotencyKey: "ingest:<relPath>:<contentHash>"
}
```

- **一文档一条目**：id 由 relPath 确定性派生，重摄入 = 同 id 新版本（版本化 CAS 既有语义），不产生重复条目
- **增量判定**：contentHash 与条目当前版本一致 → 跳过；文档删除 → v1 不处理（条目保留，后续由记忆管理者清理）
- 溯源自动：MemoryPipeline 附加 sourceTraces；memory_tx 事件自动入账本

## 5. 任务投递窗口与周期流

| 投递策略 | 机制 | v1 用法 |
|---|---|---|
| 定时投递 | timed-trigger：ScheduledJobsStore 注册 job → 到期触发（caller="timed-trigger"）→ 策略解析器自动路由 weighted | 周期流：到期 → **系统级运行摄入管道** → 有增量 → 为每个变更文档派发"语义分解"任务 |
| PTL 投递 | `/lab scheduler dispatch <role> <task...> --strategy <s> [--agent <id>]` + 摄入管道直调 | 人工派发语义分解任务；人工运行摄入 |

周期流的实现路径（计划阶段三选一，语义不变）：a) timed-trigger job 携带系统钩子类型（到期先跑管道再派发）；b) 摄入模块自带周期定时器（setInterval + 管道 + 派发）；c) 复用 timed-trigger 派发、由执行侧识别系统任务。推荐 a/b（机械行为不进 agent 路径）。

**新增代码**：周期流的接线（管道触发 + 增量派发）是本设计的新代码之一（纠正前稿"零新代码"表述）。

"窗口开闭"（池空关窗、坏任务回流）属于未来任务池+分选器语义，v1 不实现。

## 6. 语义分解任务类型（记忆管理者 v1 工作）

- **任务文本内嵌协议**（v1 无独立协议存储）：
  1. 读取指定文档（任务文本给出 relPath）
  2. 识别可独立成立的语义事实：定义 / 决策 / 规则 / 结论 / 不变量
  3. 每条事实写一个 MemoryEntry：kind=fact，anchors=文档标签+更细主题锚点，content=事实本身+源指针（`源: <relPath>`）
  4. 不改写原文档、不删除指针条目
- **执行者**：workloop agent（装配层已挂载 sdk.memory.write/retrieve）
- **调度方式**：PTL 投递 direct（v1 演示确定性）或定时投递 weighted（解析器自动）均可
- **验收标准**：产出条目 ≥1；全部锚点非空；指针条目未被破坏；memory_tx 事件留痕

## 7. 检索与热度（复用，零新代码）

- 唯一入口 `sdk.memory.retrieve({ anchors })`；条目层统一（指针条目与原子条目同库同检索）
- hitCount 旁路计数 = 热度（记忆系统设计 §2 不变量 6），v1 不加热度报表——事件已在账本，热度评价循环随记忆管理者角色完整化时再做

## 8. 边界与诚实声明

1. **模型可用性前置**：语义分解任务的真实执行依赖 workloop 会话模型可用（联邦烟测已知该环境前置可能不满足）。验收分两级：**机械链路**（摄入/幂等/增量/检索/任务派发参数）必须实测绿；**agent 真实执行链路**用 mock runner 覆盖，真实执行标注为环境前置项
2. **零行为变更**：摄入是新模块 + 一个 timed-trigger job 注册；不改既有文件行为语义（测试命令、import 惯例遵循 agent-lab 现状）
3. **文档删除不回收**：源文档被删后指针条目残留——已知边界，清理是记忆管理者职责（后续任务类型）
4. **标签无治理**：纯路径推导，无去重/归并——同义标签爆炸的治理是记忆管理者+分析者后续工作

## 9. 测试策略

- **单测**（node:test）：tags.ts 推导规则（含日期前缀/根直属文件/多级目录边界）；docs-source.ts（title/firstPara 提取、hash 稳定性）；pipeline.ts（新建/跳过/更新三分支、幂等键形态）
- **集成测**：真实 MemoryStore 落盘（隔离目录）——两连跑幂等、改动文档触发新版本、retrieve 命中 + hitCount 递增
- **任务链路测**：mock runner 断言语义分解任务的派发参数（role/task/strategy）与 timed-trigger job 注册形状
- **回归**：agent-lab 全量 `npm test`（weighted-scorer-bootstrap 2 个既有失败忽略）+ 根仓库 vitest + lint
