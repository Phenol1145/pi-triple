## 摘要

本 spec 定义 Pi-Triple 联邦的**抽象骨架模型**——一套使"联邦 = 在给定资源限制下，自组织计算结构完成任务的系统"得以成立的核心概念与公理。它是后续联邦引导（子项目 E）、容器化编排（子项目 F）、以及"逐步构建/上传/调试联邦"工作流的**理论基础**。

模型为**纯概念模型**：不与现有代码绑定，但与已实施的 economy / assembly / memory 子系统**语义锚定**（见 §6）。

**核心结构**：联邦是一个**有宽度、有深度**的计算图系统——
- **系统计算图**（静态骨架，治理顶层，可序列化）→ **生成** → **实例计算图**（动态运行层）。
- **宽度** = 每层水平展开（多节点/多通路）；**深度** = 治理的垂直嵌套（图即节点的递归）。

## §1 本体（Ontology）

联邦骨架由以下实体构成。

### 1.1 节点（Node）
联邦中承担责任、行使权利的计算主体。

- **责任（Responsibility）**：节点能完成的**任务类别**（它该做什么）。
- **权利（Rights）**：节点可调用的实际资源——**抽象说法，由两层实现**：
  - **访问权限（Access）**：节点被允许执行的操作类别（它能访问什么）。
  - **额度（Quota）**：节点可消耗的资源量（它能用多少）。
  - **关键关系**：被治理体系最多只能享有「**治理体系的权限** + **自身的额度**」——权限自上而下授予，额度自上而下分配/自身积累。
- 形态：AI agent（装配的 AgentInstance）、人类 operator（操作者）、或**抽象节点**（见 1.3 图即节点）。

### 1.2 图（Graph）
节点与其连接关系构成的计算结构。三种形态：

- **系统计算图（System Graph）**：静态/机制层的固定拓扑 = **骨架**（固定拓扑 + 空位 + 机制性通路）。**治理顶层**，可序列化，存 PTH。
- **实例计算图（Instance Graph）**：动态/运行层的进程态——某任务实际走的 agent 路径。不可序列化，只能观测/记录。
- **子图（Subgraph）**：被同一节点治理的图片段。**治理边界 = 子图边界 = 可独立部署单元**。

### 1.3 图即节点（Graph-as-Node）—— 递归与深度
一个图可被**抽象为一个节点**，从而被更高层节点治理；该图节点自身也可治理下层图。

- 系统计算图抽象为节点 → 治理运行层。
- 治理的递归嵌套产生联邦的**深度**（每层治理 = 深度 +1；子图是深度的载体）。
- 与**宽度**正交：宽度 = 每层水平展开（规模），深度 = 治理嵌套层级（组织层级）。
- **递归终止（原子节点判据）**：递归在**原子节点**终止——一个节点是**原子节点**，当且仅当它不治理任何子图（其内部不含被治理的下层图）。原子节点是最小的执行单元（如单个 AI agent）；非原子节点 = 治理子图的图节点（如组织）。并非所有节点都可无限展开为图。

### 1.4 构件 / 更新包（Component / Update-Package）
可单独上传的**变更载荷**（代码 + 数据 + 元数据），上传到某空位生效。

- **部署态**的变更载体，非运行时计算节点。
- 例：优化器、调度器、一组记忆文件。
- **特殊构件**：修改骨架本身的更新包（开新槽 / 改拓扑——见 §3.1 骨架演化）。

### 1.5 空位（Slot）
骨架**预定义**但未绑定具体实现的位置，构件填槽生效。

### 1.6 通路（Path）
计算图中的连接 / 流向。按**层**与**类型**两个维度分：

- **按层**：**机制性通路**（系统计算图的边）/ **实例性通路**（实例计算图的边——运行时 agent 实际连接）。
- **按类型**（机制性通路进一步分）：
  - **相位通路**：执行顺序的时序约束（如 market-runner 的 execute → review → settle——约束"谁先谁后"）。
  - **数据通路**：价值 / 信息的流转（如 org 垫付链、memory 沉淀链、voucher 循环——约束"什么流向哪里"）。
  - 二者同构为骨架的边：相位通路管时序，数据通路管流。

### 1.7 法律（Law）
**治理节点在创立其治理的运行图时，施加给该图的约束条件**（立法的产物）。

- **主体** = 治理节点（立法者）；**客体** = 被治理的图。
- **作用**：在最低程度上规定**受治理体系的最大权利**（权限上限 + 额度上限）和**最少责任**（责任下限）。
- **地位**：创立运行图的**必要步骤**——无法律 = 图不可运行（节点行为无约束 ≠ 有效计算结构）。
- **二态**：自然语言表述（语义意图，供人/LLM 理解）+ 算法实现（可执行强制——见 §8 遗留：强制侧的代码实现）。
- **层级**：治理嵌套 → 法律分层（上层法律约束下层图；下层不得违反上层）。
- **与责任/权利的关系**：法律是治理者**塑造被治理者「责任⇄权利」的工具**——通过立法规定图中各节点的责任范围与权利上限。

### 1.8 信任链（Trust Chain）
信任链是联邦骨架的**横切关切**（非独立实体）——见 §7 开放问题（概念尚未收敛，多模型会谈补全）。

## §2 公理（Axioms）

五条公理，从联邦定义推导，彼此一致。

- **A1 · 资源限制公理**：联邦在有限资源下运行。每个节点的**权利**（可调用资源）有限且可计量。
  - 锚定：credit / 凭证（物理锚定 token/时间/存储）= 权利的形式化。

- **A2 · 责任⇄权利平衡公理**：任何节点的**责任**与**权利**必须**平衡且一致**——承担多大责任须配多大权利，反之亦然。
  - 平衡维持 = **软硬约束并存**（依权利类型与被约束主体）：物理资源 → 硬约束（额度耗尽 = 停机）；信誉/权限 → 软约束（履职能力指标/结算激励）。
  - **优先级**：硬约束为底、软约束为调节——额度耗尽必停机，信誉只在有资源时调节（非对称）。
  - 锚定：**经济机制（结算/课税/履职能力指标）= 此公理的执行器**。

- **A3 · 治理任务公理**：治理（**立法** → 生成/修改/使用图）本身是一种**计算任务**——是治理节点的**责任**，并消耗其**权利**（治理/立法不是免费的元操作，要结算）。

- **A4 · 顶层自治理公理**：**系统计算图是治理顶层**——治理所有下层图，但其自身无更高治理者（修改系统计算图的行为由其内部节点承担）。
  - **宪法性权限（Constitutional Access）**：顶层节点治理/修改骨架所消耗的权限 = **宪法性权限**——不被更高层分配、是系统计算图自带的权限源（其余一切权限皆为其子集/下游）。这解决了"顶层权利从哪来"的自指：顶层治理消耗宪法性权限 + 节点自身额度。
  - 锚定：operator 是系统计算图**内**的治理节点（非图外之神）。

- **A5 · 图生图公理**：**系统计算图生成实例计算图**——骨架每承接一个任务，实例化出一条实例通路。运行层受系统计算图治理。
  - 宽度 = 实例化展开；深度 = 治理嵌套。

## §3 骨架与空位（Skeleton & Slots）

### 3.1 骨架的存在与演化
- **初始骨架独立存在**（可序列化，存 PTH），非纯由构件推导。
- **骨架随联邦发展迭代**：骨架更新 = **特殊构件**（一种专门修改骨架的更新包——开新槽/改拓扑）。

### 3.2 空位的来源
- **空位 = 骨架预定义**（非构件自带）——骨架先声明有哪些槽，构件填槽。
- 空位使"逐步上传"成为"填槽"：联邦骨架定义后，各部分作为填料逐步上传绑定。

## §4 关系与运作（Relations & Operations）

### 4.1 治理（Governance）
- **定义**：节点对图的**立法 → 生成/修改/使用**的责任关系。**立法是创立运行图的必要步骤**。
- **层级**：系统计算图（顶）→ 向下治理 → 子图 → … → 运行层。
- **产生深度**：每嵌套一层治理，联邦深度 +1。

### 4.2 部署（Deployment）
构件上传到空位并生效：
- **增量**：新构件加入空位，不影响既有（热加）。
- **替换**：新构件顶替旧实现——按必要性分级（§4.3）：非必要可热替换，必要需协调。
- **生效条件**：构件 → 信任链验证（§7 开放）→ 填槽生效。

### 4.3 必要性（Criticality）
构件/通路的 **必要 / 非必要** 分级：
- **必要通路**：阻断 → 系统瘫痪（如中央池循环、主市场闭环）。
- **非必要通路**：阻断 → 系统降级但仍运行（如边缘 agent、可选子市场）。
- **部署含义**：机制/配置**热更**，agent 实例**冷替换**（分级原则）。

### 4.4 法律（Law）
见 §1.7——治理节点对其图立法，规定被治理节点的最大权利（权限+额度上限）与最少责任。

### 4.5 调试（Debug / Operator 接入）
operator 节点（人类/AI 操作者）接入空位，对子图局部调试：
- **PTL（本地）**：operator 作为图节点接入子图（外部连接），调试局部而非整个联邦。
- **PTH（生产）**：**非必要不引入人类**——联邦自治，operator 是例外通道（治理/仲裁/兜底）。
- **安全性**：接入**非必要通路**调试安全；接入**必要通路**需谨慎（可能瘫痪系统）。
- **权限边界**：operator 只能调试其**直接治理的子图**（调试=治理行为 A3，消耗权限+额度）；跨治理边界调试需该子图的治理者授权。

### 4.6 加入与退出（Join / Leave）
节点进入/离开联邦的语义：
- **加入（Join）**：节点经**填槽**（上传构件绑定空位）或**装配**（新 AgentInstance）进入联邦——进入即受所在图的法律约束。
- **退出（Leave）**：分**优雅退出**（完成在手责任→释放额度→解绑空位→离开）与**强制驱逐**（违规/额度耗尽——破产机制，见 §8 遗留）。
- **责任转移**：节点退出时，其在手未完成任务按所在图的法律处置（回流市场重投/治理者接管）；空位重新开放待填。

### 4.7 空位空缺状态机（Slot Vacancy）
空位未填时的行为：
- **必要空位空缺** → 该机制性通路**阻断**，相关实例计算图**不可生成**（阻塞语义）；
- **非必要空位空缺** → **跳过**该相位/降级运行；
- **空缺超时** → 告警进 operator 通道（治理者介入：补填/降级/立法调整）。

## §5 联邦的完整图景（整合）

```
        【系统计算图 = 治理顶层 · 骨架】（可序列化，存 PTH）
         固定拓扑 + 空位 + 机制性通路 + 顶层法律
              │ 治理（立法→生成/修改/使用——计算任务）
              ▼
        【子图】（治理嵌套——深度；治理边界=子图边界=部署单元）
              │ 治理
              ▼
        【运行层 = 实例计算图】（进程态——宽度展开）

节点：{ 责任（任务类别）⇄ A2 平衡 ⇄ 权利（资源）}  受法律约束（责任范围+权利上限）
构件（更新包）：变更载荷 → 上传填槽 → 生效（增量/替换；必要/非必要分级）
联邦：在资源限制（A1）下，自组织计算结构（治理/图生图 A3/A5）完成任务的系统
```

**宽度与深度**：联邦是二维结构——宽度 = 每层水平展开（规模），深度 = 治理垂直嵌套（组织层级）。二者正交：可宽而浅（大量扁平 agent），可窄而深（多层组织嵌套）。

## §6 与现有语义锚定（Anchoring）

> 原则：抽象概念与已实施子系统**语义对应**（非代码映射）。

| 骨架概念 | 锚定语义 | 说明 |
|---|---|---|
| 节点（责任/权利） | economy **结算/凭证** + elo | A2 平衡由经济机制执行：完成任务赚 credit、调用资源烧 credit/凭证、elo 衡量责任履行信誉 |
| 系统计算图（骨架） | economy **市场闭环 §5.1 相位结构** + **任务类型注册表** | 固定拓扑 = 机制性通路；任务类型注册 = 开放槽位声明 |
| 机制性通路 | market-runner 相位流（**相位通路——时序约束**）；org 垫付链 / memory 沉淀链 / voucher 循环（**数据通路——价值/信息流转**） | 两类通路同构为骨架的边：相位通路管执行顺序，数据通路管价值/信息流（见 §1.6 修正） |
| 实例性通路 | 某任务实际走的 agent 路径 | 运行时动态产生 |
| 空位 | 已注册未承接的**任务类型**（静态预定义槽位） | 骨架预定义，待填充（注：「等 bid 的任务/等评审的市场」是**运行时动态空位**——骨架静态空位 vs 实例动态空位需区分，见 §8 遗留） |
| 子图 / 图即节点 / 治理 | economy **组织（org）**——**诚实降级：当前实现为平面垫付结构**（org_members 平面成员表，无嵌套）。嵌套市场树（组织对内治理子市场、对外单一节点）是**目标态，待实现**（见 §8 遗留） | 组织是子图/治理深度的**候选**实例；当前仅平面垫付，治理嵌套未实例化 |
| 构件（更新包） | 优化器/调度器/记忆文件等可独立上传单元 | 部署态变更载荷 |
| **法律** | memory **规则链**：公域 rule / 私域 rule（自然语言意图侧）+ 语言体系四层（EBNF/方言/语义约束——语法解析侧） | **诚实标注**：rule 当前是「LLM 可读的语法/行为声明」，**算法强制侧（可执行拦截）未实现**——法律的二态中「算法强制」待实现（见 §8 遗留）；当前锚定仅覆盖自然语言 + 语法解析侧 |
| 信任链（开放） | memory **溯源数组**（sourceTraces）+ **审核链** + 公理（自我担保） | 见 §7 |
| operator | **治理角色（人类/AI 统一）** | **诚实标注**：operator 当前**不在** RESERVED_IDS（该集合仅 central-pool/calibration-executor）——operator 在代码中仅是普通 agent，其「治理顶层」语义**待实现**（见 §8 遗留） |
| 资源限制（权利） | economy **凭证物理锚定**（token/时间/存储）+ 凭证耗尽=停机 | 权利形式化 + 硬约束 |

**锚定意义**：联邦骨架非凭空新体系——其概念在已有子系统均有语义对应；反之，economy/assembly/memory 是这个抽象模型的**具体实例**（经济机制 = A2 平衡执行器；记忆系统 = 法律/信任载体；组织 = 子图/治理深度实例）。

## §7 开放问题：信任链（Trust Chain）

> **状态**：概念未收敛——本文档暂记为开放问题，待**多模型会谈**补全后升级为正式章节。

### 7.1 初步认识（高度抽象、语境相关）

信任链 = "**可靠性如何被担保**"的抽象模式：**除元信任对象外，任何数据（含代码）必须有另一部分数据承诺其可靠性；信任链最终收敛到少数元信任对象**。

不同语境下有不同实例：

| 语境 | 待证命题 | 信任链构造 | 元信任对象 |
|---|---|---|---|
| 记忆条目可解析 | "每条目必须可解析" | 条目 → rule（约束其生成）→ base | rule 链 + base |
| 记忆信息可信 | "每条目描述的信息可信" | 条目间引用链 + append-only 证据 | 引用链 + append-only |
| 计算结果可信 | "每个节点的计算结果可信" | 每个结果附其信任链 | （待定） |

**抽象模式**：命题 P 的真，经由担保链收敛到元信任对象（自证/无需担保的根）。不同命题有不同链与不同元信任对象。

### 7.2 已决的属性

- **声明式**（非强制拦截）：信任链是**可审计的记录**，不在构件生效前强制验证（2026-08-05 裁决）。

### 7.3 补全计划：多模型会谈

- **形式**：4 个不同模型**各自独立**给出信任链的形式化理解（定义 + 结构 + 与联邦骨架的关系 + 实例化模式），汇总找共识/分歧 → 对抗性质疑 → 收敛草案 → 裁决。
- **阵容**：deepseek-v4-pro · deepseek-v4-flash · minimax-m3 · kimi-k3-256。
- **输入**：本 §7 的三种语境实例 + 抽象模式 + 联邦骨架模型全文。
- **产出**：信任链正式章节（定义/结构/与治理/法律/构件的关系/实例化）。

## §8 范围与非目标

**范围**（本 spec 覆盖）：
- 联邦骨架的核心抽象：本体（§1）/ 公理（§2）/ 骨架与空位（§3）/ 关系与运作（§4）。
- 与现有子系统的语义锚定（§6）。
- 信任链作为开放问题（§7）。

**非目标**（后续子项目处理）：
- **不做代码映射**：本 spec 是概念模型，落地实现（骨架序列化格式/构件上传接口/空位寻址）属子项目 E/F。
- **不写部署/运行细节**：PTH 容器编排、PTL 上传 CLI 的工程设计在各自 spec。
- **信任链完整形式化**（§7 会谈补全后另行评审）。

**遗留问题**（首轮对抗性评审识别，后续版本或子项目补全）：
- **破产机制**：主体额度耗尽的处理——不同联邦实现可不同（本 spec 不定死）。
- **履职能力指标**：elo 不是最终形态——需"描述运行主体履行职责能力"的指标（待补充）。
- **法律的算法强制侧**：当前 rule 是"LLM 可读的语法/行为声明"，可执行拦截未实现。
- **operator 治理语义**：operator 当前不在 RESERVED_IDS，其治理顶层地位待实现。
- **嵌套治理子图**：org 当前为平面垫付结构，嵌套市场树待实现。
- **静态空位 vs 动态空位**：骨架预定义空位（任务类型）与运行时动态空位（等 bid 任务/等评审市场）的区分。

## 附：核心概念速查

| 概念 | 一句话 |
|---|---|
| 联邦 | 资源限制下自组织计算结构完成任务的系统 |
| 节点 | 承担责任（任务类别）/行使权利（资源）的主体 |
| 系统计算图（骨架） | 静态固定拓扑+空位+机制通路；治理顶层；可序列化 |
| 实例计算图 | 动态运行层；进程态 |
| 子图 | 被同一节点治理的图片段（治理边界=部署单元） |
| 图即节点 | 图抽象为节点被治理——产生深度 |
| 构件（更新包） | 可单独上传的变更载荷（代码+数据+元数据） |
| 空位 | 骨架预定义待填槽位 |
| 责任 | 节点能完成的任务类别 |
| 权利 | = 访问权限（能访问什么）+ 额度（能用多少）；被治理体系最多享「治理体系权限+自身额度」 |
| 通路 | 按层（机制性/实例性）× 按类型（相位时序/数据流） |
| 法律 | 治理节点创立运行图时施加的约束（自然语言+算法；规定被治理者最大权利+最少责任） |
| 宪法性权限 | 系统计算图顶层权限——不被分配、其余权限之源（A4） |
| 原子节点 | 不治理任何子图的节点（递归终止判据） |
| 信任链 | 可靠性担保链，收敛到元信任对象（开放） |
| 责任⇄权利 | 必须平衡一致（A2——经济机制执行；硬约束为底、软约束为调节） |
| 宽度/深度 | 水平展开规模 / 治理嵌套层级 |
